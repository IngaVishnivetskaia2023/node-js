## Event Loop deep dive

### Reactor Pattern
The Reactor Pattern is a high-level description of how Node.js works under the hood. Let's start with the big picture before diving into the details.

🐦 Reactor Pattern — это архитектурный паттерн для обработки множества конкурентных I/O операций одним потоком. Node.js построен на этом паттерне.

#### Главный вопрос, который он решает:
Как **один поток** может обслуживать тысячи **одновременных I/O операций** (сетевые соединения, чтение файлов), не блокируясь ни на одной из них?

There are 3 primary components: **Event Demultiplexer, Event Loop, and Event Queue**.

The algorithm behind the Reactor Pattern:

1. The Event Demultiplexer receives a request for an I/O operation and delegates it to the appropriate hardware (steps 1–3 in the diagram below).
2. Once the I/O request is processed (for example, data from a file is ready to be read), the Event Demultiplexer adds the registered callback to the Event Queue (steps 4–5).
3. The Event Loop takes those callbacks and executes them sequentially until the Event Queue is empty (step 6).
4. If there are no events in the Event Queue, the Event Loop gives control back to the Event Demultiplexer.
5. If there are no pending I/O operations registered in the Event Demultiplexer, the application exits.

### Что такое Event Demultiplexer
Почему «демультиплексор»?
Термин из электроники/телекома:
- Мультиплексор (MUX) — объединяет много сигналов в один канал
- Демультиплексор (DEMUX) — разделяет один канал обратно на много сигналов

В контексте I/O:
```
Тысячи источников I/O (сокеты, файлы, таймеры)
              │
              ▼
    ┌─────────────────────┐
    │  DEMULTIPLEXER      │  ← один системный вызов наблюдает
    │  (epoll_wait)       │     за ВСЕМИ источниками сразу
    └──────────┬──────────┘
               │
               ▼
    "Сокет #47 готов к чтению"    ← конкретное уведомление
    "Сокет #183 готов к записи"      для конкретного ресурса
    "Таймер #12 истёк"
```

Одна точка наблюдения → множество конкретных событий. Это и есть де-мультиплексирование.

#### Что это конкретно на уровне ОС
Event Demultiplexer — это абстракция. В реальности это системные вызовы ядра:

| ОС | Механизм | Системный вызов |
| :-- | :-- | :-- |
| Linux | epoll | epoll_create(), epoll_ctl(), epoll_wait() |
| macOS/BSD | kqueue | kqueue(), kevent() |
| Windows | IOCP | CreateIoCompletionPort(), GetQueuedCompletionStatus() |
| Linux 5.1+ | io_uring | io_uring_setup(), io_uring_enter() |


🐦  `libuv` — это C-библиотека внутри Node.js, которая абстрагирует эти OS-специфичные механизмы **в единый кроссплатформенный API**:

```
// Внутри libuv (упрощённо):
#if defined(__linux__)
  // использует epoll
  int nfds = epoll_wait(epoll_fd, events, MAX_EVENTS, timeout);
#elif defined(__APPLE__)
  // использует kqueue
  int nfds = kevent(kq, NULL, 0, events, MAX_EVENTS, &timeout);
#elif defined(_WIN32)
  // использует IOCP
  GetQueuedCompletionStatus(port, &bytes, &key, &overlapped, timeout);
#endif
```

### Алгоритм по шагам — конкретный пример
Допустим, у нас HTTP-сервер и клиент отправляет запрос:
```
const server = require('http').createServer((req, res) => {
  fs.readFile('./data.json', (err, data) => {
    res.end(data);
  });
});
server.listen(3000);
```

#### Шаг 1–3: Регистрация I/O операции
```
JS-код: server.listen(3000)
       │
       ▼
V8 вызывает C++ binding (src/tcp_wrap.cc)
       │
       ▼
libuv: uv_tcp_bind() → создаёт socket fd
libuv: uv_listen()   → bind() + listen() syscalls
       │
       ▼
libuv регистрирует socket fd в демультиплексоре:
  epoll_ctl(epoll_fd, EPOLL_CTL_ADD, server_socket_fd, {EPOLLIN})
       │
       ▼
Ядро ОС: "OK, я слежу за этим сокетом"
```

#### Шаг 3→4: Ожидание и получение события

```
Event Loop (libuv) вызывает:
  epoll_wait(epoll_fd, events, ...)
       │
       │  ← main thread СПИТ здесь
       │     (не тратит CPU, не busy-wait)
       │
       │  [клиент подключается → ядро принимает TCP handshake]
       │  [ядро будит epoll_wait: "server_socket_fd готов к accept()"]
       │
       ▼
epoll_wait возвращает: "fd=server_socket_fd, событие=EPOLLIN"
```

#### Шаг 4–5: Callback → Event Queue

```
libuv видит: "этот fd связан с TCP сервером"
       │
       ▼
libuv вызывает accept() → получает новый client_fd
libuv создаёт uv_tcp_t для клиента
       │
       ▼
libuv помещает callback (твою функцию (req, res) => {...})
в Event Queue (конкретно: в I/O callbacks фазу)
```

#### Шаг 6: Event Loop выполняет callback

```
Event Loop переходит к фазе poll/callbacks:
       │
       ▼
Берёт callback из очереди → помещает в V8 Call Stack
       │
       ▼
V8 выполняет: (req, res) => { fs.readFile('./data.json', cb) }
       │
       ▼
fs.readFile → libuv → НЕ epoll (файлы не поддерживаются epoll)
           → отправляет в THREAD POOL (uv_fs_read)
           → worker thread делает blocking read()
           → по завершении результат → обратно в Event Queue
           → Event Loop вызывает callback (err, data) => { res.end(data) }
           → res.end(data) → запись в сокет → epoll следит за записью
```

### Process vs Runtime — разграничение понятий

#### Process — концепция уровня ОС
Процесс — это единица выделения ресурсов ядром ОС (память, файловые дескрипторы, CPU time, PID).

Любая программа выполняется как процесс — неважно, написана она на C, Rust или JavaScript. Даже сам Node.js binary (/usr/local/bin/node) — это скомпилированная C++ программа, которая становится процессом при запуске.

#### Runtime — программная прослойка ВНУТРИ процесса
Runtime (среда выполнения) — это не синоним процесса. Это программный слой, который:
- Исполняет код конкретного языка
- Управляет моделью выполнения (event loop, threads, GC)
- Предоставляет API для взаимодействия с ОС

#### I/O (Input/Output) — это любое взаимодействие с внешним миром относительно CPU+RAM:

| Тип I/O | Устройство | Системный вызов |
| :-- | :-- | :-- |
| Файловый | Disk (SSD/HDD) | read(), write(), open() |
| Сетевой | NIC (Network Interface Card) | socket(), connect(), send() |
| Терминальный | TTY (keyboard → stdin, display → stdout) | read(0,...), write(1,...) |
| Межпроцессный | Pipe, Unix socket, shared memory | pipe(), sendmsg() |

CPU выполняет инструкцию `syscall`, переключается в `kernel mode`, ядро программирует контроллер устройства (через DMA, MMIO или port I/O), а затем:
- **Blocking I/O:** процесс переводится в состояние `WAITING`, пока устройство не сигнализирует прерыванием (`interrupt`)
- **Non-blocking I/O:** `syscall` возвращается немедленно с `EAGAIN`, процесс опрашивает готовность через `epoll`/`kqueue`/`io_uring`
Node.js (через `libuv`) использует `non-blocking I/O` + `event notification` для сети и `thread pool` для файловой системы (т.к. `epoll` не работает с обычными файлами на Linux).
