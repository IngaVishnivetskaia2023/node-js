#### How traditional row storage works

```
RELATIONAL DATABASE (PostgreSQL, MySQL):

  Table: user_events
  ┌────────┬────────────┬───────────┬──────────┬─────────┐
  │ id     │ user_id    │ event     │ timestamp│ device  │
  ├────────┼────────────┼───────────┼──────────┼─────────┤
  │ 1      │ u_1001     │ login     │ 10:00:00 │ mobile  │
  │ 2      │ u_1002     │ purchase  │ 10:00:01 │ desktop │
  │ 3      │ u_1001     │ logout    │ 10:05:00 │ mobile  │
  │ 4      │ u_1003     │ login     │ 10:05:01 │ tablet  │
  │ 5      │ u_1002     │ login     │ 10:06:00 │ mobile  │
  └────────┴────────────┴───────────┴──────────┴─────────┘


  HOW IT'S STORED ON DISK — row by row:

  Disk block 1:
  ┌──────────────────────────────────────────────────────────┐
  │ [1, u_1001, login, 10:00:00, mobile]                     │  ← row 1
  │ [2, u_1002, purchase, 10:00:01, desktop]                 │  ← row 2
  │ [3, u_1001, logout, 10:05:00, mobile]                    │  ← row 3
  └──────────────────────────────────────────────────────────┘

  Disk block 2:
  ┌──────────────────────────────────────────────────────────┐
  │ [4, u_1003, login, 10:05:01, tablet]                     │  ← row 4
  │ [5, u_1002, login, 10:06:00, mobile]                     │  ← row 5
  └──────────────────────────────────────────────────────────┘

  All fields of one row are stored TOGETHER, contiguously.
  id, user_id, event, timestamp, device — all adjacent on disk.


  GREAT FOR: "Give me everything about row 3"
  
    SELECT * FROM user_events WHERE id = 3;
    
    Read one disk block → get all fields → done.
    One disk seek. Fast. ✅


  BAD FOR: "Count events per device across 100 million rows"
  
    SELECT device, COUNT(*) FROM user_events GROUP BY device;
    
    Need to read EVERY row from disk.
    But you only need the "device" column.
    You're forced to read id, user_id, event, timestamp too.
    
    Reading 100 million rows × 5 columns = loading ALL data.
    But you only needed 1 column out of 5.
    80% of I/O was WASTED on columns you don't need.
```

####  Columnar storage (Redshift, ClickHouse)

```
SAME DATA, stored BY COLUMN instead of by row:

  id column file:
  ┌──────────────────────────────┐
  │ 1, 2, 3, 4, 5, 6, 7, ...     │  all IDs together
  └──────────────────────────────┘

  user_id column file:
  ┌──────────────────────────────────────────────┐
  │ u_1001, u_1002, u_1001, u_1003, u_1002, ...  │  all user_ids together
  └──────────────────────────────────────────────┘

  event column file:
  ┌────────────────────────────────────────────────────────┐
  │ login, purchase, logout, login, login, purchase, ...   │  all events together
  └────────────────────────────────────────────────────────┘

  timestamp column file:
  ┌──────────────────────────────────────────────────┐
  │ 10:00:00, 10:00:01, 10:05:00, 10:05:01, ...      │  all timestamps together
  └──────────────────────────────────────────────────┘

  device column file:
  ┌────────────────────────────────────────────────────┐
  │ mobile, desktop, mobile, tablet, mobile, ...       │  all devices together
  └────────────────────────────────────────────────────┘


  NOW: "Count events per device across 100 million rows"

    SELECT device, COUNT(*) FROM user_events GROUP BY device;

    Read ONLY the device column file.
    Skip id, user_id, event, timestamp entirely.
    
    100 million rows × 1 column vs 100 million rows × 5 columns.
    Read 1/5th the data. 5× faster I/O. ✅


  AND: columnar data COMPRESSES incredibly well:

    Row storage, device column scattered across rows:
      [1,u_1001,login,10:00:00,mobile], [2,u_1002,purchase,10:00:01,desktop], ...
      Can't compress — mixed data types, no patterns
    
    Columnar storage, device column stored together:
      mobile, desktop, mobile, tablet, mobile, mobile, desktop, mobile, ...
      
      Only 3 unique values across millions of rows!
      
      Run-length encoding:  mobile×3, desktop×1, tablet×1, mobile×2, ...
      Dictionary encoding:  0=mobile, 1=desktop, 2=tablet → 0,1,0,2,0,0,1,0
      Bit-packing:          2 bits per value (3 unique values = 2 bits)
      
      100 million strings → compressed to maybe 25 MB
      vs uncompressed: 100 million × ~7 bytes = 700 MB
      
      ~28× compression ratio. Common in real columnar databases.


  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │  WHY COLUMNAR IS FAST FOR ANALYTICS:                         │
  │                                                              │
  │  1. Read only needed columns (skip irrelevant data)          │
  │  2. Better compression (same-type values compress well)      │
  │  3. Less data to read from disk = less I/O = faster          │
  │  4. CPU cache friendly (processing one data type at a time)  │
  │  5. SIMD vectorization (process many values in one CPU op)   │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
```


#### DIFFERENT thing: Wide-Column Stores (Cassandra, HBase)

```
Wide-column stores are NOT columnar databases.
The name is misleading. They're actually ROW-ORIENTED.

Wide-column = each row can have DIFFERENT columns.
No fixed schema. Rows are "wide" (many possible columns).


RELATIONAL TABLE (fixed schema):

  Every row MUST have the same columns.

  ┌──────────┬───────┬─────────┬────────┐
  │ user_id  │ name  │ email   │ phone  │
  ├──────────┼───────┼─────────┼────────┤
  │ u_1001   │ John  │ j@az.com│ 555-01 │
  │ u_1002   │ Alice │ a@az.com│ 555-02 │
  │ u_1003   │ Bob   │ b@az.com│ 555-03 │  ← every row has all 4 cols
  └──────────┴───────┴─────────┴────────┘

  Want to add "twitter_handle" for just one user?
  ALTER TABLE → adds column to ALL rows. Most are NULL.


WIDE-COLUMN STORE (flexible schema):

  Each row has a ROW KEY and any number of COLUMN:VALUE pairs.
  Different rows can have completely different columns.

  Row Key     │ Columns
  ────────────┼──────────────────────────────────────────────
  u_1001      │ name:John, email:j@az.com, phone:555-01
  u_1002      │ name:Alice, email:a@az.com, twitter:@alice
  u_1003      │ name:Bob, dept:research, badge:A-4521, floor:3
  u_1004      │ name:Carol

  Row u_1001 has 3 columns.
  Row u_1002 has 3 columns (different set — twitter instead of phone).
  Row u_1003 has 4 columns (completely different — dept, badge, floor).
  Row u_1004 has 1 column.

  No ALTER TABLE needed. Each row defines its own columns.
  That's why it's called "wide" — rows can have thousands of columns.
```

#### Cassandra data model — concrete example

```
Cassandra organizes data as:

  Keyspace → Table → Partition → Rows → Columns


EXAMPLE: IoT sensor readings

  CREATE TABLE sensor_readings (
    sensor_id    TEXT,
    reading_date DATE,
    reading_time TIMESTAMP,
    temperature  DOUBLE,
    humidity     DOUBLE,
    pressure     DOUBLE,
    PRIMARY KEY ((sensor_id, reading_date), reading_time)
  );
  --             ^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^
  --             PARTITION KEY             CLUSTERING KEY
  --             (determines which node)   (sort order within partition)


  Data on disk — grouped by partition:

  ┌──────────────────────────────────────────────────────────────┐
  │ PARTITION: (sensor_id=S001, reading_date=2025-01-15)         │
  │                                                              │
  │  reading_time    │ temperature │ humidity │ pressure         │
  │  ────────────────┼─────────────┼──────────┼─────────         │
  │  10:00:00        │ 22.5        │ 45.0     │ 1013.2           │
  │  10:01:00        │ 22.6        │ 44.8     │ 1013.1           │
  │  10:02:00        │ 22.7        │ 44.9     │ 1013.3           │
  │  ... (1440 readings per day) ...                             │
  │                                                              │
  │  All stored CONTIGUOUSLY on disk.                            │
  │  Sorted by reading_time (clustering key).                    │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │ PARTITION: (sensor_id=S001, reading_date=2025-01-16)         │
  │                                                              │
  │  reading_time    │ temperature │ humidity │ pressure         │
  │  ────────────────┼─────────────┼──────────┼─────────         │
  │  10:00:00        │ 21.0        │ 50.2     │ 1010.5           │
  │  ...                                                         │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │ PARTITION: (sensor_id=S002, reading_date=2025-01-15)         │
  │                                                              │
  │  reading_time    │ temperature │ humidity │ battery          │
  │  ────────────────┼─────────────┼──────────┼─────────         │
  │  10:00:00        │ 19.5        │ 60.1     │ 87%              │
  │  ...                                                         │
  │                                                              │
  │  ↑ DIFFERENT COLUMNS than S001! S002 has battery, no pressure│
  │    This is the "wide" part — flexible columns per row        │
  └──────────────────────────────────────────────────────────────┘
```

#### How Cassandra stores data on disk

```
Cassandra writes are INCREDIBLY fast because of its storage engine:


  WRITE PATH:

    Client: INSERT INTO sensor_readings ...
    
    Step 1: Write to COMMIT LOG (append-only file on disk)
            Sequential write. Fastest possible disk I/O.
            This is the durability guarantee.
            
    Step 2: Write to MEMTABLE (in-memory sorted structure)
            RAM write. Nanoseconds.
            
    Step 3: Return success to client. DONE.
            
            That's it. Two operations. Both fast.
            No "find the row, update in place, rewrite page."
            No B-tree traversal. No random disk I/O.


    ┌────────────────────────────────────────────────────┐
    │                                                    │
    │  Client → Commit Log (sequential disk write)       │
    │        → Memtable (RAM)                            │
    │        → ACK to client                             │
    │                                                    │
    │  Later (background):                               │
    │  Memtable fills up → FLUSH to SSTable on disk      │
    │                                                    │
    └────────────────────────────────────────────────────┘


  SSTable (Sorted String Table):

    When memtable is full, it's flushed to disk as an SSTABLE.
    SSTables are IMMUTABLE. Once written, NEVER modified.

    SSTable file for partition (S001, 2025-01-15):
    ┌──────────────────────────────────────────────────┐
    │ [10:00:00, temp=22.5, hum=45.0, pres=1013.2]     │
    │ [10:01:00, temp=22.6, hum=44.8, pres=1013.1]     │
    │ [10:02:00, temp=22.7, hum=44.9, pres=1013.3]     │
    │ ... sorted by clustering key ...                 │
    └──────────────────────────────────────────────────┘

    Multiple SSTables accumulate over time.
    COMPACTION merges them periodically (background process).


  READ PATH:

    Client: SELECT * FROM sensor_readings 
            WHERE sensor_id = 'S001' AND reading_date = '2025-01-15'
            AND reading_time >= '10:00:00' AND reading_time <= '10:05:00'

    Step 1: Check memtable (RAM) for recent writes
    Step 2: Check bloom filters (probabilistic: "is this key in this SSTable?")
    Step 3: Read relevant SSTables from disk
    Step 4: Merge results, return to client

    Fast IF you query by partition key.
    Slow/forbidden if you scan across partitions.
```
