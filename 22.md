#### the core concept
```
A key-value database is the simplest possible database.
It does ONE thing: given a key, return a value.


  It's literally a dictionary / hash map / object:

  Python:    my_dict["user:123"]      → {"name": "John", "role": "admin"}
  JavaScript: myMap.get("user:123")    → {"name": "John", "role": "admin"}
  Redis:     GET user:123              → {"name": "John", "role": "admin"}


  ┌─────────────────────────┬──────────────────────────────────┐
  │  KEY                    │  VALUE                           │
  ├─────────────────────────┼──────────────────────────────────┤
  │  session:user123        │  "token-abc-xyz"                 │
  │  session:user456        │  "token-def-uvw"                 │
  │  cache:search:kras      │  "{results: [...], count: 42}"   │
  │  feature:dark_mode      │  "true"                          │
  │  rate_limit:user123     │  "47"                            │
  │  user:123:profile       │  "{name: John, dept: Research}"  │
  └─────────────────────────┴──────────────────────────────────┘

  Operations:
    GET key              → return value
    SET key value        → store value
    DELETE key           → remove entry
    EXISTS key           → does it exist?
    EXPIRE key seconds   → auto-delete after N seconds

  That's basically it. No tables. No columns. No joins.
  No WHERE clauses. No GROUP BY. No schema.
```

#### Why is it so fast?
```
HASH MAP — O(1) lookup:

  Every key is hashed to a memory address.
  No searching. No scanning. No index traversal.
  Go directly to the memory location. Read the value. Done.

  PostgreSQL: SELECT * FROM sessions WHERE token = 'abc'
  
    1. Parse SQL
    2. Plan query
    3. Check index (B-tree traversal: O(log n))
    4. Follow pointer to heap page
    5. Read row from disk (possibly from cache)
    6. Return result
    
    Time: 0.5 - 5ms (with index, from memory)
    Time: 5 - 50ms (from disk)

  Redis: GET session:token:abc
  
    1. Hash the key
    2. Look up memory address
    3. Return value
    
    Time: 0.05 - 0.1ms (always from memory)
    

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Operation          PostgreSQL        Redis              │
  │  ─────────────────  ────────────────  ──────────────     │
  │                                                          │
  │  Lookup by key      0.5 - 5 ms       0.05 - 0.1 ms       │
  │                     (10-100× slower)  (baseline)         │
  │                                                          │
  │  WHY: SQL parsing, query planning, B-tree traversal,     │
  │       disk I/O possibility — vs — direct hash lookup     │
  │       in RAM                                             │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

#### What you CAN'T do

```
Key-value databases have NO query capability beyond "get by key."


  ❌ "Find all sessions created in the last hour"
     There's no way to filter by value content.
     You'd have to GET every single key and check each one.

  ❌ "Find all users in the Research department"
     No WHERE clause. No columns. No filtering.

  ❌ "Count how many active sessions exist"
     No COUNT. No aggregation.

  ❌ "Join users with their orders"
     No joins. No relationships. No foreign keys.

  ❌ "Find sessions where token starts with 'abc'"
     No LIKE. No pattern matching on values.
     (Redis has SCAN with key pattern matching, but not value matching)

  YOU MUST KNOW THE EXACT KEY to get data.

  Know the key    → instant result     ✅
  Don't know key  → can't find it      ❌


  This is the fundamental tradeoff:
    Maximum speed for ONE access pattern (get by key).
    ZERO flexibility for anything else.
```

### Redis

#### How Redis stores data in memory
```
Redis keeps EVERYTHING in RAM. 


  YOUR SERVER:
  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  RAM (64 GB)                                               │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │                                                      │  │
  │  │  Redis process                                       │  │
  │  │  ┌────────────────────────────────────────────────┐  │  │
  │  │  │                                                │  │  │
  │  │  │  Hash table:                                   │  │  │
  │  │  │                                                │  │  │
  │  │  │  "session:u123" → "token-abc"                  │  │  │
  │  │  │  "session:u456" → "token-def"                  │  │  │
  │  │  │  "cache:search:kras" → "{results: [...]}"      │  │  │
  │  │  │  "rate:u123" → "47"                            │  │  │
  │  │  │  ... 10 million more keys ...                  │  │  │
  │  │  │                                                │  │  │
  │  │  └────────────────────────────────────────────────┘  │  │
  │  │                                                      │  │
  │  └──────────────────────────────────────────────────────┘  │
  │                                                            │
  │  Disk (1 TB)                                               │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │  RDB snapshot (periodic backup of RAM to disk)       │  │
  │  │  AOF log (append-only log for durability)            │  │
  │  │  These are for RECOVERY, not for reads.              │  │
  │  └──────────────────────────────────────────────────────┘  │
  │                                                            │
  └────────────────────────────────────────────────────────────┘


  WHY RAM?

    RAM access:  ~100 nanoseconds
    SSD access:  ~100,000 nanoseconds (100 microseconds)
    HDD access:  ~10,000,000 nanoseconds (10 milliseconds)

    RAM is 1000× faster than SSD.
    RAM is 100,000× faster than HDD.

    That's why Redis sub-millisecond. Data is already in RAM.
    No disk seeks. No page loads. Just pointer dereference.


  THE COST:

    RAM is expensive. ~$5/GB/month on AWS.
    Disk is cheap. ~$0.10/GB/month on AWS.
    
    50× more expensive per GB.
    
    That's why you use Redis for HOT data (sessions, cache).
    Not for ALL data (that's what PostgreSQL/DynamoDB is for).
```

#### Redis data structures — not just strings
```
Redis is NOT just GET/SET strings. It has rich data structures.
This is what makes it powerful beyond simple caching.


1. STRINGS — the simplest
─────────────────────────

  SET user:123:name "John"
  GET user:123:name              → "John"

  SET counter 0
  INCR counter                   → 1      (atomic increment)
  INCR counter                   → 2
  INCRBY counter 10              → 12

  SET session:abc "data" EX 3600          (expires in 1 hour)
  TTL session:abc                → 3597   (seconds remaining)

  Use cases: cache values, counters, rate limits, session tokens


2. HASHES — like a mini object/row
───────────────────────────────────

  HSET user:123 name "John" dept "Research" role "admin"
  
  HGET user:123 name             → "John"
  HGET user:123 dept             → "Research"
  HGETALL user:123               → {name: "John", dept: "Research", role: "admin"}
  
  HINCRBY user:123 login_count 1 → (atomic increment of one field)
  
  
  Like a row in a table, but accessed by key:
  
    PostgreSQL:  SELECT name FROM users WHERE id = 123
    Redis:       HGET user:123 name
    
  Difference: Redis can only get by key. Can't search by name.

  Use cases: user profiles, config objects, shopping carts


3. LISTS — ordered sequence
───────────────────────────

  LPUSH notifications:user123 "New message from Alice"
  LPUSH notifications:user123 "Your report is ready"
  LPUSH notifications:user123 "Meeting in 10 minutes"
  
  LRANGE notifications:user123 0 -1     → all notifications
  LRANGE notifications:user123 0 4      → latest 5
  
  RPOP notifications:user123             → remove oldest
  LLEN notifications:user123             → count

  Use cases: message queues, activity feeds, recent items


4. SETS — unique unordered collection
──────────────────────────────────────

  SADD online_users "user123"
  SADD online_users "user456"
  SADD online_users "user789"
  SADD online_users "user123"    → 0 (already exists, no duplicate)
  
  SMEMBERS online_users          → {"user123", "user456", "user789"}
  SISMEMBER online_users "user123"  → 1 (true)
  SCARD online_users             → 3 (count)
  
  SINTER online_users premium_users   → users who are online AND premium
  SUNION team_a team_b                → all members of either team

  Use cases: online users, tags, unique visitors, permissions


5. SORTED SETS — scored + ordered
─────────────────────────────────

  ZADD leaderboard 1500 "player_a"
  ZADD leaderboard 2300 "player_b"
  ZADD leaderboard 1800 "player_c"
  ZADD leaderboard 2100 "player_d"
  
  ZRANGE leaderboard 0 -1 WITHSCORES   → sorted low to high
    → player_a:1500, player_c:1800, player_d:2100, player_b:2300

  ZREVRANGE leaderboard 0 2            → top 3 (high to low)
    → player_b, player_d, player_c

  ZRANK leaderboard "player_c"          → 1 (0-indexed position)
  ZSCORE leaderboard "player_b"         → 2300
  ZINCRBY leaderboard 500 "player_a"    → 2000 (add to score)

  Use cases: leaderboards, priority queues, time-sorted feeds


  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Data Structure    Redis command    PostgreSQL equivalent │
  │  ────────────────  ──────────────   ──────────────────── │
  │                                                          │
  │  String            GET/SET          SELECT col           │
  │                                     FROM t WHERE id = x  │
  │                                                          │
  │  Hash              HGETALL          SELECT *             │
  │                                     FROM t WHERE id = x  │
  │                                                          │
  │  List              LRANGE           SELECT * FROM t      │
  │                                     ORDER BY created     │
  │                                     LIMIT 10             │
  │                                                          │
  │  Set               SMEMBERS         SELECT DISTINCT col  │
  │                    SINTER           INTERSECT            │
  │                                                          │
  │  Sorted Set        ZRANGE           SELECT * FROM t      │
  │                                     ORDER BY score       │
  │                                                          │
  │  Redis: O(1) to O(log n). In memory. Sub-millisecond.   │
  │  PostgreSQL: more flexible queries. Disk-based. Slower.  │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

#### Redis TTL — automatic expiration
```
The KILLER FEATURE for caching: keys expire automatically.

  SET cache:search:kras "{results: [...]}" EX 300
  #                                         ^^^^^^
  #                                         expire in 300 seconds (5 min)

  # Time 0s:    GET cache:search:kras → "{results: [...]}"
  # Time 150s:  GET cache:search:kras → "{results: [...]}"   (still valid)
  # Time 301s:  GET cache:search:kras → nil                  (expired, gone)


  WHY THIS MATTERS:

    Without TTL (manual cache):
      1. User searches "KRAS"
      2. Backend queries OpenSearch (200ms)
      3. Backend stores result in cache
      4. Next user searches "KRAS" → cache hit (1ms)
      5. ... 2 hours later, new documents indexed in OpenSearch
      6. User searches "KRAS" → gets STALE cached result ❌
      7. Need manual invalidation logic. Complex. Error-prone.

    With TTL:
      1. User searches "KRAS"
      2. Backend queries OpenSearch (200ms)
      3. Backend stores in Redis with EX 300 (5 min TTL)
      4. Next user searches "KRAS" → cache hit (1ms) ✅
      5. 5 minutes later → key auto-expires
      6. Next search → cache miss → fresh query to OpenSearch
      7. No manual invalidation needed. Self-cleaning. ✅
```

#### Redis persistence — what happens when it crashes

```
"If Redis is in-memory, do I lose everything on restart?"

  By default: potentially yes.
  With persistence configured: no.


  TWO PERSISTENCE MODES:

  1. RDB (Redis Database) — periodic snapshots
  ─────────────────────────────────────────────

    Every N seconds, Redis dumps entire dataset to disk.
    
    save 900 1      # snapshot if ≥1 key changed in 900 seconds
    save 300 10     # snapshot if ≥10 keys changed in 300 seconds
    save 60 10000   # snapshot if ≥10000 keys changed in 60 seconds
    
    Creates: dump.rdb (binary file, full dataset)
    
    On restart: load dump.rdb → back to last snapshot.
    
    RISK: lose data between last snapshot and crash.
    If snapshot was 5 minutes ago → lose 5 minutes of data.
    
    For cache: fine. Cache data is regenerable.
    For sessions: user might need to re-login. Acceptable.


  2. AOF (Append Only File) — log every write
  ────────────────────────────────────────────

    Every write command is appended to a log file.
    
    AOF file contents:
      SET session:u123 "token-abc" EX 3600
      SET session:u456 "token-def" EX 3600
      INCR rate_limit:u123
      INCR rate_limit:u123
      SET cache:search:kras "{...}" EX 300
      DEL session:u123
      ...
    
    On restart: replay the AOF → exact state recovery.
    
    appendfsync options:
      always     → fsync after every write (safest, slowest)
      everysec   → fsync once per second (good balance)
      no         → let OS decide (fastest, least safe)
    
    RISK with everysec: lose at most 1 second of data.


  AWS ElastiCache / MemoryDB:
    AWS manages this for you.
    MemoryDB: durable (multi-AZ, transaction log). Won't lose data.
    ElastiCache: cache-oriented. Can lose data. That's fine for cache.
```

#### Real example: session storage

```
# User sessions in Redis:

async def login(username: str, password: str) -> str:
    user = await db.verify_credentials(username, password)
    
    # Create session token
    session_id = secrets.token_urlsafe(32)
    
    # Store session in Redis (expires in 24 hours)
    r.hset(f"session:{session_id}", mapping={
        "user_id": user.id,
        "username": user.username,
        "role": user.role,
        "department": user.department,
        "logged_in_at": datetime.now().isoformat(),
    })
    r.expire(f"session:{session_id}", 86400)  # 24 hours
    
    return session_id


async def get_current_user(session_id: str) -> dict | None:
    # Every API request checks the session
    session = r.hgetall(f"session:{session_id}")
    
    if not session:
        return None  # expired or invalid
    
    return session


async def logout(session_id: str):
    r.delete(f"session:{session_id}")  # instant invalidation
```

#### Real example: rate limiting
```
# Rate limit: max 10 requests per minute per user

async def check_rate_limit(user_id: str) -> bool:
    key = f"rate_limit:{user_id}"
    
    # INCR atomically increments (creates key with value 1 if doesn't exist)
    current = r.incr(key)
    
    if current == 1:
        # First request — set expiry to 60 seconds
        r.expire(key, 60)
    
    if current > 10:
        return False  # rate limited ❌
    
    return True  # allowed ✅
```

### DynamoDB

#### How DynamoDB is different from Redis
```
┌────────────────────────────┬──────────────────────────────────┐
│  Redis                     │  DynamoDB                        │
├────────────────────────────┼──────────────────────────────────┤
│  In-memory                 │  On disk (SSD)                   │
│  Sub-millisecond           │  Single-digit milliseconds       │
│  Data lost if no persist.  │  Durable (replicated across AZs) │
│  You manage the server     │  Fully serverless (no server)    │
│  (or use ElastiCache)      │                                  │
│  Fixed capacity (RAM size) │  Auto-scales infinitely          │
│  Best for: cache, temp     │  Best for: primary data store    │
│  Cheap at small scale      │  Pay per request or capacity     │
│  Open source               │  AWS proprietary                 │
└────────────────────────────┴──────────────────────────────────┘


ANALOGY:

  Redis = sticky notes on your desk
    Instant access. Limited space. Notes fall off if desk flips.
    Great for reminders, temp info. Not for permanent records.

  DynamoDB = filing cabinet with infinite drawers
    Slightly slower (open drawer, find folder). But permanent.
    Never runs out of space. Never loses anything.
    Great for primary data that must survive.
```

#### DynamoDB data model
```
DynamoDB has TABLES. Each item (row) has:
  - Partition key (required): determines which server stores it
  - Sort key (optional): allows range queries within a partition
  - Attributes: any number of fields (flexible schema, like wide-column)


EXAMPLE: Chat sessions for your app

  Table: ChatSessions
  Partition key: session_id
  Sort key: turn_number

  ┌──────────────────────┬─────────────┬──────────────────────────────┐
  │ session_id (PK)      │ turn (SK)   │ Attributes                   │
  ├──────────────────────┼─────────────┼──────────────────────────────┤
  │ sess_abc123          │ 1           │ user_query: "KRAS?"          │
  │                      │             │ answer: "KRAS inhibitors..." │
  │                      │             │ model: "anthropic"           │
  │                      │             │ timestamp: "2025-01-15T10:00"│
  │                      │             │ citations: [{...}, {...}]    │
  ├──────────────────────┼─────────────┼──────────────────────────────┤
  │ sess_abc123          │ 2           │ user_query: "Side effects?"  │
  │                      │             │ answer: "Common side..."     │
  │                      │             │ model: "anthropic"           │
  │                      │             │ timestamp: "2025-01-15T10:01"│
  ├──────────────────────┼─────────────┼──────────────────────────────┤
  │ sess_abc123          │ 3           │ user_query: "Clinical trials"│
  │                      │             │ answer: "Several phase III.."│
  │                      │             │ temperature: 0.7             │
  ├──────────────────────┼─────────────┼──────────────────────────────┤
  │ sess_def456          │ 1           │ user_query: "HPP treatment?" │
  │                      │             │ answer: "Asfotase alfa..."   │
  │                      │             │ filters: {source: "MSL"}     │
  └─────────��────────────┴─────────────┴──────────────────────────────┘

  Notice:
    - Different items have different attributes (flexible schema)
    - Turn 1 has citations, turn 2 doesn't
    - Turn 3 has temperature, others don't
    - sess_def456 has filters, sess_abc123 doesn't
    - This is the "document" aspect of DynamoDB


  QUERIES YOU CAN DO:

    ✅ Get one item:
       PK = "sess_abc123", SK = 2
       → instant, single item

    ✅ Get all turns in a session:
       PK = "sess_abc123"
       → returns turns 1, 2, 3 sorted by sort key

    ✅ Get turns 1-2 only:
       PK = "sess_abc123", SK BETWEEN 1 AND 2

    ❌ Find all sessions that mention "KRAS":
       Can't search by attribute value without a scan.
       Must know the partition key.

    ❌ Find all sessions by user:
       user_id is not the partition key.
       Need a GSI (Global Secondary Index) for this.
```

#### DynamoDB scaling — how it works
```
PARTITIONING:

  DynamoDB spreads data across many servers by partition key.

  hash("sess_abc123") → server 7
  hash("sess_def456") → server 3
  hash("sess_ghi789") → server 12

  ┌──────────┐  ┌──────────┐  ┌──────────┐     ┌──────────┐
  │ Server 1 │  │ Server 2 │  │ Server 3 │ ... │ Server N │
  │          │  │          │  │          │     │          │
  │ sess_xyz │  │ sess_mno │  │ sess_def │     │ sess_pqr │
  │ sess_tuv │  │ sess_jkl │  │ sess_stu │     │ sess_wxy │
  └──────────┘  └──────────┘  └──────────┘     └──────────┘

  Need more capacity? DynamoDB adds more servers automatically.
  You don't know. You don't manage. It just scales.

  1 request/second or 1,000,000 requests/second: same API.
  DynamoDB adjusts behind the scenes.


  THIS IS WHY IT'S "SERVERLESS":

    Redis:
      You pick an instance: cache.r6g.large (13 GB RAM, 2 vCPU)
      If you exceed 13 GB → you must upgrade instance
      If traffic spikes → you must add replicas
      You manage capacity.

    DynamoDB:
      You create a table. No instance. No server. No capacity planning.
      
      Two pricing modes:
      
      On-demand:  pay per request ($1.25 per million writes)
                  zero capacity planning
                  scales instantly
                  
      Provisioned: set read/write capacity units
                   cheaper if traffic is predictable
                   auto-scaling can adjust capacity

```
