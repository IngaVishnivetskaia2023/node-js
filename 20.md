#### Docker vs Podman — what's different
```
Docker architecture (the OLD way):

  $ docker run nginx
  
  ┌──────────────────────────────────────────────────────────────┐
  │  Your terminal                                               │
  │  (docker CLI)                                                │
  │       │                                                      │
  │       │ API call (HTTP over Unix socket)                     │
  │       ▼                                                      │
  │  ┌──────────────────────┐                                    │
  │  │  Docker Daemon       │  ← ALWAYS RUNNING as root (PID 1)  │
  │  │  (dockerd)           │     a background service           │
  │  │                      │     owns ALL containers            │
  │  │  runs as: root       │     single point of failure        │
  │  │  PID: 1234           │     if daemon crashes → ALL        │
  │  │                      │     containers die                 │
  │  └──────────┬───────────┘                                    │
  │             │                                                │
  │             │ manages                                        │
  │             ▼                                                │
  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐        │
  │  │ Container 1  │  │ Container 2  │  │ Container 3  │        │
  │  │ (nginx)      │  │ (postgres)   │  │ (redis)      │        │
  │  │ child of     │  │ child of     │  │ child of     │        │
  │  │ dockerd      │  │ dockerd      │  │ dockerd      │        │
  │  └──────────────┘  └──────────────┘  └──────────────┘        │
  │                                                              │
  │  ALL containers are children of the DAEMON.                  │
  │  NOT children of your terminal/shell.                        │
  └──────────────────────────────────────────────────────────────┘


  Problems with Docker daemon:

    1. ROOT ACCESS REQUIRED
       dockerd runs as root. Always.
       Anyone who can talk to Docker socket = effectively root.
       $ docker run -v /:/host ubuntu rm -rf /host  ← deletes host OS
       
    2. SINGLE POINT OF FAILURE
       dockerd crashes → every container dies
       dockerd upgrade → restart all containers
       
    3. ALWAYS RUNNING
       daemon consumes resources even when no containers running
       
    4. SECURITY SURFACE
       one long-running root daemon = juicy attack target



Podman architecture (the NEW way):

  $ podman run nginx

  ┌──────────────────────────────────────────────────────────────┐
  │  Your terminal                                               │
  │  (podman CLI)                                                │
  │       │                                                      │
  │       │ directly forks the container process                 │
  │       ▼                                                      │
  │  ┌──────────────┐                                            │
  │  │ Container 1  │  ← direct child of YOUR shell              │
  │  │ (nginx)      │     no daemon in between                   │
  │  │ runs as:     │     runs as YOUR user (not root)           │
  │  │ your user    │     PID visible in normal ps output        │
  │  └──────────────┘                                            │
  │                                                              │
  │  NO DAEMON. No background service. No root.                  │
  │                                                              │
  │  $ podman run postgres                                       │
  │       │                                                      │
  │       ▼                                                      │
  │  ┌──────────────┐                                            │
  │  │ Container 2  │  ← another direct child of your shell      │
  │  │ (postgres)   │     independent of container 1             │
  │  │ runs as:     │     if container 1 crashes, 2 is fine      │
  │  │ your user    │                                            │
  │  └──────────────┘                                            │
  │                                                              │
  │  Each container is an independent process.                    │
  │  No central daemon managing them.                            │
  │  No single point of failure.                                 │
  └──────────────────────────────────────────────────────────────┘


  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Feature           Docker             Podman             │
  │  ───────────────   ─────────────────  ────────────────── │
  │                                                          │
  │  Architecture      daemon (dockerd)   daemonless         │
  │  Runs as           root               your user          │
  │  Container parent  daemon process     your shell         │
  │  Daemon crash      all containers die no daemon to crash │
  │  CLI commands      docker run/build   podman run/build   │
  │  Compatibility     N/A                docker-compatible  │
  │  Systemd support   workarounds        native             │
  │  Root required     yes (default)      no (rootless)      │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

#### How containers work under the hood (Linux kernel)

```
Containers are NOT virtual machines.
Containers are regular Linux PROCESSES with restrictions.

A container uses TWO Linux kernel features:


FEATURE 1: NAMESPACES (isolation — what the process can SEE)
────────────────────────────────────────────────────────────

  Namespaces make a process think it's alone on the machine.

  ┌─────────────────────────────────────────────────────────────┐
  │ Namespace     │ What it isolates         │ Effect           │
  ├───────────────┼──────────────────────────┼──────────────────┤
  │ PID           │ Process IDs              │ Container sees   │
  │               │                          │ its PID as 1     │
  │               │                          │ can't see host   │
  │               │                          │ processes        │
  │               │                          │                  │
  │ Network       │ Network interfaces, IPs  │ Container gets   │
  │               │                          │ its own IP,      │
  │               │                          │ its own ports    │
  │               │                          │                  │
  │ Mount         │ Filesystem mounts        │ Container sees   │
  │               │                          │ its own /        │
  │               │                          │ not host's /     │
  │               │                          │                  │
  │ UTS           │ Hostname                 │ Container has    │
  │               │                          │ its own hostname │
  │               │                          │                  │
  │ User          │ User/Group IDs           │ UID 0 in         │
  │               │                          │ container ≠      │
  │               │                          │ UID 0 on host    │
  │               │                          │                  │
  │ IPC           │ Inter-process comms      │ Isolated shared  │
  │               │                          │ memory           │
  └───────────────┴──────────────────────────┴──────────────────┘

  Example: PID namespace

    Host machine sees:
      PID 1     systemd
      PID 432   sshd
      PID 1001  podman
      PID 1002  nginx          ← container process
      PID 1003  nginx worker   ← container process

    Inside container sees:
      PID 1     nginx          ← thinks it's PID 1
      PID 2     nginx worker
      
      "I'm the only thing running. I am PID 1."
      Can't see systemd, sshd, podman, or anything else.


  Example: Mount namespace

    Host filesystem:
      /
      ├── bin/
      ├── etc/
      ├── home/john/projects/
      └── var/lib/containers/overlay/abc123/
          └── merged/          ← container's root filesystem
              ├── bin/         (from container image)
              ├── etc/
              └── app/

    Container sees:
      /                        ← this is actually .../merged/
      ├── bin/                 from the container image
      ├── etc/                 NOT the host's /bin, /etc
      └── app/                 completely isolated filesystem
      
      Can't see /home/john. Can't see host files.


FEATURE 2: CGROUPS (limits — what the process can USE)
──────────────────────────────────────────────────────

  Cgroups limit how much resources a process can consume.

  Without cgroups:
    Container runs: while True: malloc(1GB)
    → eats ALL host memory → host crashes → everything dies

  With cgroups:
    $ podman run --memory=512m --cpus=1.5 myapp
    
    Container can use MAX:
      512 MB RAM    → tries to use more → OOM killed
      1.5 CPU cores → tries to use more → throttled

  ┌────────────────────────────────────────────────────────┐
  │                                                        │
  │  cgroup resource        podman flag                    │
  │  ──────────────────     ──────────────────────         │
  │  Memory limit           --memory=512m                  │
  │  CPU cores              --cpus=2                       │
  │  CPU shares (priority)  --cpu-shares=512               │
  │  Disk I/O bandwidth     --blkio-weight=300             │
  │  PIDs limit             --pids-limit=100               │
  │                                                        │
  └───────────────────────────────────────────────────────┘


SUMMARY: what a container really is:

  container = process + namespaces + cgroups

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  Regular process:                                   │
  │    sees all processes, all files, all network       │
  │    can use unlimited CPU and memory                 │
  │                                                     │
  │  Containerized process:                             │
  │    sees only its own processes (PID namespace)      │
  │    sees only its own filesystem (mount namespace)   │
  │    has its own network (network namespace)          │
  │    limited CPU and memory (cgroups)                 │
  │                                                     │
  │  Same kernel. Same machine. Just restricted view.   │
  │                                                     │
  │  VM:        separate kernel, separate OS, heavy     │
  │  Container: shared kernel, isolated view, light     │
  │                                                     │
  └─────────────────────────────────────────────────────┘
```

#### Container images — the filesystem layer

```
An IMAGE is a blueprint. A CONTAINER is a running instance.

  Image = class
  Container = object (instance of that class)


HOW IMAGES ARE BUILT — layers:

  Dockerfile:

    FROM python:3.11-slim          ← Layer 1: base OS + Python
    WORKDIR /app                   ← Layer 2: create directory
    COPY requirements.txt .        ← Layer 3: copy requirements file
    RUN pip install -r req...      ← Layer 4: install dependencies
    COPY src/ ./src/               ← Layer 5: copy source code
    CMD ["python", "src/main.py"]  ← metadata (not a layer)

  Each instruction creates a LAYER:

    ┌─────────────────────────────────┐
    │ Layer 5: COPY src/ (2 MB)       │  your code
    ├─────────────────────────────────┤
    │ Layer 4: pip install (150 MB)   │  dependencies
    ├─────────────────────────────────┤
    │ Layer 3: COPY requirements.txt  │  tiny file
    ├─────────────────────────────────┤
    │ Layer 2: WORKDIR /app           │  metadata
    ├─────────────────────────────────┤
    │ Layer 1: python:3.11-slim       │  Debian + Python
    │          (120 MB)               │  
    └─────────────────────────────────┘

  Layers are:
    - READ-ONLY (immutable, never change after creation)
    - SHARED between containers (10 containers from same image share layers, not 10 copies)
    - CACHED (rebuild only changed layers)


OVERLAY FILESYSTEM — how containers write:

  Image layers are read-only. But containers need to write files.
  Solution: OverlayFS.

    ┌────────────────────────────────────────┐
    │  Container writable layer              │  ← new/modified files
    │  (thin, per-container)                 │     go here
    ├────────────────────────────────────────┤
    │  Image Layer 5 (read-only)             │
    ├────────────────────────────────────────┤
    │  Image Layer 4 (read-only)             │
    ├────────────────────────────────────────┤
    │  Image Layer 3 (read-only)             │
    ├────────────────────────────────────────┤
    │  Image Layer 2 (read-only)             │
    ├────────────────────────────────────────┤
    │  Image Layer 1 (read-only)             │
    └────────────────────────────────────────┘

  Reading /app/config.json:
    OverlayFS checks from top to bottom:
      Writable layer has it? → use that version.
      Layer 5? Layer 4? ... → use first found.

  Writing /app/newfile.txt:
    Written to the writable layer ONLY.
    Image layers unchanged.
    
  Modifying /etc/hosts (from base image):
    Copy from image layer → writable layer (copy-on-write).
    Modify in writable layer.
    Image layer still has original.

  Container deleted → writable layer deleted.
  Image layers remain. Unchanged. Shared. Cached.
```

#### Podman's rootless magic

```
DOCKER: runs as root. Container processes are root's children.

PODMAN: runs as YOUR user. Container processes are YOUR children.


HOW ROOTLESS WORKS:

  Problem: namespaces require root (CAP_SYS_ADMIN capability).
  How can a regular user create namespaces?
  
  Answer: USER namespaces.
  
  Linux kernel allows unprivileged users to create a USER namespace.
  Inside that namespace, the user IS root (UID 0).
  But that "root" maps to your regular user on the host.

  ┌──────────────────────────────────────────────────┐
  │                                                  │
  │  Host:                                           │
  │    User: john (UID 1000)                         │
  │    $ podman run -it ubuntu bash                  │
  │                                                  │
  │  Container:                                      │
  │    User: root (UID 0)     ← looks like root      │
  │    # whoami                                      │
  │    root                                          │
  │    # id                                          │
  │    uid=0(root) gid=0(root)                       │
  │                                                  │
  │  Host reality:                                   │
  │    $ ps aux | grep bash                          │
  │    john  5432 ... bash    ← runs as john, not root│
  │                                                  │
  │  Mapping (in /etc/subuid):                       │
  │    john:100000:65536                             │
  │                                                  │
  │    Container UID 0  → Host UID 100000            │
  │    Container UID 1  → Host UID 100001            │
  │    Container UID 65535 → Host UID 165535         │
  │                                                  │
  │  If container "root" escapes:                    │
  │    It's UID 100000 on the host.                  │
  │    An unprivileged user. Can't do anything.      │
  │    Can't read /etc/shadow. Can't install packages.│
  │    Harmless.                                     │
  │                                                  │
  │  If Docker container root escapes:               │
  │    It's UID 0 on the host.                       │
  │    Actual root. Game over.                       │
  │                                                  │
  └──────────────────────────────────────────────────┘
```

#### Containerfile (Dockerfile) — building images with Podman

```
# Podman uses the SAME Dockerfile format.
# Convention: name it "Containerfile" (but "Dockerfile" also works).

# ── Stage 1: Build ──────────────────────────────────────────

FROM python:3.11-slim AS builder

WORKDIR /app

# Install system dependencies needed for building Python packages
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc libpq-dev && \
    rm -rf /var/lib/apt/lists/*

# Copy only requirements first (layer caching optimization)
COPY requirements.txt .

# Install Python dependencies into a virtual env
RUN python -m venv /opt/venv && \
    /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

# Copy source code
COPY src/ ./src/


# ── Stage 2: Production (smaller image) ─────────────────────

FROM python:3.11-slim

WORKDIR /app

# Install only runtime dependencies (not build tools)
RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*

# Copy corporate CA certificate
COPY certs/astrazeneca-root-ca.pem /usr/local/share/ca-certificates/
RUN update-ca-certificates

# Copy virtual env from builder (no gcc, no pip cache, no headers)
COPY --from=builder /opt/venv /opt/venv

# Copy source code
COPY --from=builder /app/src ./src/

# Use venv Python
ENV PATH="/opt/venv/bin:$PATH"

# Don't run as root inside container
RUN useradd --create-home appuser
USER appuser

# Expose port (documentation, doesn't actually open port)
EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"

# Start the app
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]

```




```
MULTI-STAGE BUILD explained:

  Stage 1 (builder):
    - Has gcc, development headers, pip
    - Compiles C extensions (numpy, psycopg2, etc.)
    - Large: ~800MB
    
  Stage 2 (production):
    - Only runtime libraries (libpq5, not libpq-dev)
    - Copies compiled venv from stage 1
    - No gcc, no pip, no build tools
    - Small: ~200MB

  Final image only contains stage 2.
  Stage 1 is discarded after build.
  
  800MB during build → 200MB in production.
```


```
# Build the image
podman build -t myapp:1.0.0 .

# What happens:
#   1. Podman reads Containerfile
#   2. For each instruction (FROM, RUN, COPY):
#      - Creates a temporary container
#      - Executes the instruction
#      - Snapshots the filesystem as a new layer
#      - Destroys the temporary container
#   3. Tags the final stack of layers as "myapp:1.0.0"

# Layer caching:
#   If requirements.txt hasn't changed since last build:
#     Layer 1 (FROM):        cached ✅ (skip)
#     Layer 2 (WORKDIR):     cached ✅ (skip)
#     Layer 3 (apt-get):     cached ✅ (skip)
#     Layer 4 (COPY req):    cached ✅ (file unchanged)
#     Layer 5 (pip install): cached ✅ (previous layer unchanged)
#     Layer 6 (COPY src):    REBUILD ❌ (source code changed)
#
#   Only rebuilds from the first changed layer downward.
#   pip install (slow, 30s) is SKIPPED if requirements unchanged.
#   This is why COPY requirements.txt comes BEFORE COPY src/.
```

#### Local development workflow

```
SCENARIO: Python FastAPI backend with PostgreSQL and Redis


  project/
  ├── src/
  │   ├── main.py
  │   ├── routes/
  │   └── services/
  ├── tests/
  ├── Containerfile
  ├── compose.yaml            ← defines all services
  ├── requirements.txt
  └── .env
```

```
# compose.yaml (works with podman-compose or docker-compose)

services:

  app:
    build: .                          # build from ./Containerfile
    ports:
      - "8000:8000"                   # host:container
    volumes:
      - ./src:/app/src:Z              # mount source code for hot reload
      #                 ^
      #                 Z = SELinux label (needed on Fedora/RHEL)
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/myapp
      - REDIS_URL=redis://cache:6379
      - OPENAI_API_KEY=${OPENAI_API_KEY}     # from .env or host env
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    command: uvicorn src.main:app --host 0.0.0.0 --reload
    #                                           ^^^^^^^^
    #        --reload watches for file changes (hot reload)
    #        combined with volume mount: edit on host → reloads in container

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"                   # expose for local DB tools
    volumes:
      - pgdata:/var/lib/postgresql/data    # persist data across restarts
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine
    ports:
      - "6379:6379"

volumes:
  pgdata:                             # named volume, persists data
```



```
# Start everything
podman compose up

# What happens:
#   1. Podman pulls postgres:16-alpine (if not cached)
#   2. Podman pulls redis:7-alpine (if not cached)
#   3. Podman builds your app from Containerfile
#   4. Creates a virtual network (containers can talk by service name)
#   5. Starts db, waits for healthcheck to pass
#   6. Starts cache
#   7. Starts app (connects to db:5432 and cache:6379)

# Your app is now running at http://localhost:8000
# PostgreSQL at localhost:5432
# Redis at localhost:6379


# Development flow:
#   1. Edit src/routes/search.py on your HOST machine
#   2. Volume mount syncs the change into the container
#   3. uvicorn --reload detects the change
#   4. App reloads with new code
#   5. Test at http://localhost:8000
#   No rebuild needed. Instant feedback.


# Stop everything
podman compose down

# Stop and DELETE all data (clean slate)
podman compose down -v    # -v removes volumes (database data)
```

#### Podman on macOS — the hidden VM
```
IMPORTANT: containers are a LINUX kernel feature.
macOS doesn't have namespaces or cgroups.
Neither does Windows.

So how does podman work on macOS/Windows?

  $ podman machine init    # creates a Linux VM
  $ podman machine start   # starts the VM

  ┌─────────────────────────────────────────────────────┐
  │  Your macOS                                         │
  │                                                     │
  │  ┌───────────────────────────────────────────────┐  │
  │  │  Linux VM (Fedora CoreOS, managed by Podman)  │  │
  │  │  Runs via Apple Virtualization Framework      │  │
  │  │  (or QEMU on older macs)                      │  │
  │  │                                                │  │
  │  │  Linux kernel 6.x                             │  │
  │  │  ├── namespaces ✅                             │  │
  │  │  ├── cgroups ✅                                │  │
  │  │  └── overlayfs ✅                              │  │
  │  │                                                │  │
  │  │  Containers run HERE, inside the VM:          │  │
  │  │  ┌─────────┐ ┌─────────┐ ┌─────────┐         │  │
  │  │  │ app     │ │ db      │ │ cache   │         │  │
  │  │  └─────────┘ └─────────┘ └─────────┘         │  │
  │  │                                                │  │
  │  └───────────────────────────────────────────────┘  │
  │                                                     │
  │  podman CLI on macOS talks to the VM via SSH/API    │
  │  Port forwarding: macOS:8000 → VM:8000 → app:8000  │
  │                                                     │
  └─────────────────────────────────────────────────────┘

  Docker Desktop does the SAME thing (runs a Linux VM).
  Podman Machine does the SAME thing.
  
  On macOS/Windows: container tool = Linux VM manager + CLI.
  On Linux: no VM needed. Containers run directly on host kernel.
```

#### From local to production — the pipeline
```

STEP 1: Local development (your laptop)
────────────────────────────────────────

  $ podman compose up
  
  - App, DB, Redis all running locally
  - Volume mounts for hot reload
  - Edit code → instant reload
  - Test at localhost:8000


STEP 2: CI/CD pipeline (GitHub Actions / Jenkins)
──────────────────────────────────────────────────

  .github/workflows/deploy.yml:

    - name: Build image
      run: podman build -t myapp:${{ github.sha }} .
    
    - name: Run tests
      run: podman run myapp:${{ github.sha }} pytest
    
    - name: Push to ECR
      run: |
        podman login --username AWS --password $(aws ecr get-login-password) \
          123456789.dkr.ecr.eu-west-1.amazonaws.com
          
        podman tag myapp:${{ github.sha }} \
          123456789.dkr.ecr.eu-west-1.amazonaws.com/myapp:${{ github.sha }}
          
        podman push \
          123456789.dkr.ecr.eu-west-1.amazonaws.com/myapp:${{ github.sha }}

  What happens:
    1. Build SAME Containerfile as local
    2. Run tests INSIDE the container (same environment as production)
    3. Push image to AWS ECR (container registry)
    

STEP 3: Production (AWS ECS)
─────────────────────────────

  ECS Task Definition:

    {
      "containerDefinitions": [{
        "name": "myapp",
        "image": "123456789.dkr.ecr.eu-west-1.amazonaws.com/myapp:abc123",
        //        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
        //        SAME image that was built in CI and tested
        //        SAME image that ran on your laptop (minus volume mounts)
        "portMappings": [{ "containerPort": 8000 }],
        "memory": 512,
        "cpu": 256,
        "environment": [
          { "name": "DATABASE_URL", "value": "..." },
          { "name": "REDIS_URL", "value": "..." }
        ],
        "healthCheck": {
          "command": ["CMD-SHELL", "curl -f http://localhost:8000/health"],
          "interval": 30,
          "timeout": 5,
          "retries": 3
        }
      }]
    }

  ECS pulls the image from ECR.
  Runs it on EC2 or Fargate.
  Same container. Same binary. Same dependencies.


THE FULL JOURNEY:

  ┌─────────────┐     ┌─────────────┐     ┌─────────────────┐
  │ Local dev   │     │ CI/CD       │     │ Production      │
  │             │     │             │     │                 │
  │ podman      │────→│ podman      │────→│ ECR → ECS       │
  │ compose up  │     │ build       │     │                 │
  │             │     │ test        │     │ Same image ✅    │
  │ localhost   │     │ push to ECR │     │ Same deps  ✅    │
  │ :8000       │     │             │     │ Same OS    ✅    │
  │             │     │             │     │ Same Python✅    │
  └─────────────┘     └─────────────┘     └─────────────────┘

  "Works on my machine" = works everywhere.
  Because it IS the same machine (container).
```

#### Essential Podman commands
```
# ── Images ──────────────────────────────────────────

podman build -t myapp:1.0.0 .           # build from Containerfile
podman images                             # list local images
podman pull python:3.11-slim             # download image from registry
podman push myapp:1.0.0 registry/myapp   # upload to registry
podman rmi myapp:1.0.0                   # delete image


# ── Containers ──────────────────────────────────────

podman run -d -p 8000:8000 myapp:1.0.0   # run in background
podman run -it ubuntu bash                # run interactive shell
podman ps                                  # list running containers
podman ps -a                               # list ALL (including stopped)
podman logs my-container                   # view stdout/stderr
podman logs -f my-container                # follow logs (tail -f)
podman exec -it my-container bash          # shell into running container
podman stop my-container                   # graceful stop (SIGTERM)
podman kill my-container                   # force stop (SIGKILL)
podman rm my-container                     # delete stopped container


# ── Compose ─────────────────────────────────────────

podman compose up                          # start all services
podman compose up -d                       # start in background
podman compose up --build                  # rebuild images first
podman compose down                        # stop and remove
podman compose down -v                     # also remove volumes
podman compose logs -f app                 # follow logs for one service


# ── Debugging ───────────────────────────────────────

podman inspect my-container                # all container metadata (JSON)
podman top my-container                    # processes inside container
podman stats                               # CPU/memory usage (like htop)
podman port my-container                   # port mappings
podman diff my-container                   # files changed vs image


# ── Cleanup ─────────────────────────────────────────

podman system prune                        # remove unused data
podman system prune --all                  # remove EVERYTHING unused
podman volume prune                        # remove unused volumes
```
