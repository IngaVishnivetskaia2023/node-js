## Two Instrumentation Engines — Istanbul vs V8

|  | Istanbul | V8 (native) |
| :-- | :-- | :-- |
| How it works | Rewrites your SOURCE CODE (AST transform) before running | Uses Chrome/Node's BUILT-IN coverage tracking |
| Speed | Slower (extra transform step) | Faster (native, no code rewriting) |
| Accuracy | Very precise, mature | Slightly less granular for some edge cases historically, now very close |
| Default in | Jest | Vitest (recommended default) |

#### Core Concept
Coverage measures what **percentage of your CODE** actually got **EXECUTED** while running your tests. 
It's calculated by instrumenting your code (injecting tracking counters) before running tests, then reporting which parts were/weren't hit.

#### The FOUR Coverage Metrics

```
┌─────────────────────────────────────────--------------────┐
│  1. STATEMENTS   → % of individual statements executed    │
│  2. BRANCHES        → % of if/else, ternary, switch       │
│                        PATHS taken                        │
│  3. FUNCTIONS     → % of functions CALLED at least once   │
│  4. LINES                → % of code LINES executed       │
└───────────────────────────────────────--------------──────┘
```

```
// utils.js
function getDiscount(user, amount) {    // ← FUNCTION
  if (user.isPremium) {                 // ← BRANCH point
    return amount * 0.8;             // ← STATEMENT/LINE
  } else {
    return amount * 0.95;            // ← STATEMENT/LINE
  }
}
```

```
Branches measure DECISION POINTS specifically.
Even if 75% of LINES ran, only 50% of POSSIBLE PATHS
through your if/else logic were actually exercised —
this is why branch coverage is often the STRICTEST metric.
```

#### How It's Actually Calculated (Under the Hood)
```
┌─────────────────────────────────────────────┐
│  STEP 1: INSTRUMENTATION                    │
│  Before running tests, your source code is  │
│  rewritten to inject invisible COUNTERS:    │
│                                             │
│  function getDiscount(user, amount) {       │
│    __coverage__.functions[0]++;  ← injected │
│    if (user.isPremium) {                    │
│      __coverage__.branches[0][0]++;  ← injected │
│      return amount * 0.8;                   │
│    } else {                                 │
│      __coverage__.branches[0][1]++;  ← injected │
│      return amount * 0.95;                  │
│    }                                        │
│  }                                          │
├─────────────────────────────────────────────┤
│  STEP 2: RUN TESTS                          │
│  As tests execute, these counters increment │
│  every time that code path is HIT           │
├─────────────────────────────────────────────┤
│  STEP 3: REPORT GENERATION                  │
│  After all tests finish, counters are read  │
│  and converted into percentages per file/folder│
└─────────────────────────────────────────────┘
```

#### Tools that do the instrumentation:
```
Jest    → uses Istanbul (via babel-plugin-istanbul) by default
Vitest    → uses v8 (Chrome's built-in coverage) OR Istanbul,
              configurable via `coverage.provider`
```

```
// vitest.config.ts
export default {
  test: {
    coverage: {
      provider: 'v8', // or 'istanbul'
      reporter: ['text', 'html', 'lcov'],
      thresholds: {
        statements: 80,
        branches: 75,
        functions: 80,
        lines: 80,
      },
    },
  },
};
```

#### Coverage Thresholds — Enforcing Minimums
```
// jest.config.js
module.exports = {
  coverageThreshold: {
    global: {
      branches: 80,
      functions: 80,
      lines: 80,
      statements: 80,
    },
  },
};
```

```
If ANY metric falls BELOW its threshold,
the test run FAILS (exit code non-zero) —
commonly used to BLOCK a PR/CI pipeline
if coverage drops below an agreed minimum.
```

#### Visualizing Uncovered Code (HTML Report)
```
jest --coverage --coverageReporters=html
# generates coverage/index.html
```

#### ❗ Important Caveat — Coverage ≠ Quality
```
Coverage tells you: "this line of code RAN during tests"
Coverage does NOT tell you: "this line's BEHAVIOR was VERIFIED correct"

100% coverage with weak assertions still leaves you
exposed to bugs — coverage is a FLOOR, not a GUARANTEE.
```

Coverage tools instrument your code with invisible counters before running tests, 
track which statements/branches/functions/lines actually execute, then report percentages. 
`Jest` defaults to `Istanbul`, `Vitest` defaults to the faster native `V8` engine — both produce the same four core metrics (statements, branches, functions, lines). It's a useful signal for finding untested code paths, 
but high coverage alone doesn't guarantee your tests actually verify correct behavior — that still depends on writing meaningful assertions.
