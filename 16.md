#### The Core Idea

```
Client doesn't know (or care) what's between it and the server.
Server doesn't know (or care) what's between it and the client.

Each layer only talks to the layer NEXT to it.


  SIMPLE (what client thinks):

    Browser ──────────────────────→ Server
    "I send request, I get response. That's all I know."


  REALITY (what actually happens):

    Browser → CloudFront → ALB → nginx → FastAPI
                │            │       │
                │            │       └── TLS termination
                │            └────────── load balancing
                └─────────────────────── caching + geographic routing


  The browser sends the EXACT SAME request regardless of
  how many layers exist. Zero code changes on client.

  You can ADD, REMOVE, or REPLACE any layer
  and neither client nor server code changes.
```

#### Why this matters

```
Think of it like postal mail:

  You write a letter to "123 Main Street, New York."
  
  You don't know:
    - Which post office sorts it
    - Which truck carries it
    - Whether it goes through a regional hub
    - Whether the mailman walks or drives
    - Whether the building has a doorman who receives it
  
  You just put it in the mailbox. It arrives.
  
  The postal service can:
    - Add a new sorting facility (performance)
    - Reroute around a closed road (reliability)  
    - X-ray your letter at customs (security)
    - Store copies of common letters locally (caching)
  
  You change NOTHING about how you write letters.
  The recipient changes NOTHING about how they read them.


  HTTP works the same way:
    Browser writes: GET /api/search HTTP/1.1
    Server reads:   GET /api/search HTTP/1.1
    
    Everything in between is transparent.
```

#### Every layer explained with what it does to the request
```
FULL PATH through your ANSWER app:

  ┌───────────┐
  │  Browser  │  GET /api/v2/search
  └─────┬─────┘  Authorization: Bearer eyJ...
        │        Content-Type: application/json
        │        {"query":"cardiovascular outcomes"}
        │
        ▼
  ┌───────────────────────────────────────────────────────┐
  │  LAYER 1: DNS (Route 53)                              │
  │                                                       │
  │  Browser asks: "What IP is answer.astrazeneca.com?"   │
  │  DNS responds: "13.225.89.42" (CloudFront edge IP)    │
  │                                                       │
  │  What it does:                                        │
  │    - Resolves domain name to IP address               │
  │    - Can route to different IPs based on geography    │
  │    - Health checks: if one IP is down, return another │
  │                                                       │
  │  Client knows: nothing. Browser handles DNS silently. │
  │  Server knows: nothing. Doesn't know DNS exists.      │
  └───────────────────┬───────────────────────────────────┘
                      │
                      ▼
  ┌───────────────────────────────────────────────────────┐
  │  LAYER 2: CDN (CloudFront)                            │
  │                                                       │
  │  Edge server in user's region receives request.       │
  │                                                       │
  │  Checks: is /api/v2/search cached?                    │
  │    API POST request → NO (POST is not cacheable)      │
  │    → forwards to origin (ALB)                         │
  │                                                       │
  │  But if request were: GET /assets/index-a1b2c3.js     │
  │    Checks cache → YES, cached! → return immediately   │
  │    Request never reaches your server.                  │
  │    Response served from edge server 50ms away,         │
  │    not origin server 200ms away.                       │
  │                                                       │
  │  What it does:                                        │
  │    - Caches static responses (JS, CSS, images)        │
  │    - TLS termination (decrypts HTTPS)                 │
  │    - DDoS protection (absorbs attack traffic)         │
  │    - Geographic routing (serve from nearest edge)     │
  │    - Compression (gzip/brotli)                        │
  │                                                       │
  │  Client knows: nothing. Same HTTPS request.           │
  │  Server knows: nothing. Sees normal HTTP request.     │
  └───────────────────┬───────────────────────────────────┘
                      │
                      ▼
  ┌───────────────────────────────────────────────────────┐
  │  LAYER 3: Load Balancer (ALB)                         │
  │                                                       │
  │  Receives request from CloudFront (or directly).      │
  │                                                       │
  │  Has 3 ECS containers:                                │
  │    Container A: healthy, 40% CPU                      │
  │    Container B: healthy, 60% CPU                      │
  │    Container C: unhealthy (failing health checks)     │
  │                                                       │
  │  Decision: route to Container A (least loaded)        │
  │                                                       │
  │  What it does:                                        │
  │    - Distributes requests across containers           │
  │    - Health checks (removes sick containers)          │
  │    - TLS termination (if no CDN in front)             │
  │    - Path-based routing (/api/* → API, /* → frontend) │
  │    - Sticky sessions (optional)                       │
  │    - Connection draining (graceful shutdown)          │
  │                                                       │
  │  Client knows: nothing. Sees one server.              │
  │  Server knows: nothing. Sees normal HTTP request.     │
  │    (ALB adds X-Forwarded-For header with client IP)   │
  └───────────────────┬───────────────────────────────────┘
                      │
                      ▼
  ┌───────────────────────────────────────────────────────┐
  │  LAYER 4: Reverse Proxy (nginx — if used)             │
  │                                                       │
  │  Sits inside the container, in front of uvicorn.      │
  │                                                       │
  │  What it does:                                        │
  │    - Buffers slow client connections                  │
  │      (client sends body slowly, nginx collects it,    │
  │       sends to uvicorn all at once — frees worker)    │
  │    - Serves static files directly (no Python needed)  │
  │    - Rate limiting per IP                             │
  │    - Request size limits (reject 100MB uploads)       │
  │    - Compression                                      │
  │    - Multiple uvicorn workers behind one nginx        │
  │                                                       │
  │  Client knows: nothing.                               │
  │  Server knows: nothing. Sees normal HTTP request.     │
  │    (nginx adds X-Real-IP header)                      │
  └───────────────────┬───────────────────────────────────┘
                      │
                      ▼
  ┌───────────────────────────────────────────────────────┐
  │  LAYER 5: Application Server (uvicorn + FastAPI)      │
  │                                                       │
  │  FINALLY: your Python code runs.                      │
  │                                                       │
  │  FastAPI sees:                                        │
  │    method: POST                                       │
  │    path: /api/v2/search                               │
  │    headers: Authorization, Content-Type                │
  │    body: {"query":"cardiovascular outcomes"}           │
  │                                                       │
  │  FastAPI has NO IDEA about:                           │
  │    - CloudFront caching in front                      │
  │    - ALB balancing across containers                  │
  │    - nginx buffering connections                      │
  │    - DNS routing by geography                         │
  │                                                       │
  │  It just processes the request and returns a response.│
  └───────────────────────────────────────────────────────┘
```


#### Each layer solves a specific problem
```

┌────────────────┬──────────────────────────────────────────────────┐
│ Layer          │ Problem it solves                                │
├────────────────┼──────────────────────────────────────────────────┤
│ DNS            │ "Where is this server?"                          │
│                │ Maps domain → IP. Enables geographic routing.    │
│                │ Failover: if primary down, route to secondary.   │
├────────────────┼──────────────────────────────────────────────────┤
│ CDN            │ "This server is far away."                       │
│                │ Caches content at edge locations worldwide.      │
│                │ 50ms vs 200ms for static files.                  │
│                │ Absorbs traffic (DDoS protection).               │
├────────────────┼──────────────────────────────────────────────────┤
│ Load Balancer  │ "One server can't handle all traffic."           │
│                │ Distributes across multiple servers.             │
│                │ Removes unhealthy servers automatically.         │
│                │ Enables zero-downtime deployments.               │
├────────────────┼──────────────────────────────────────────────────┤
│ Reverse Proxy  │ "Application server shouldn't handle everything."│
│                │ Buffers slow connections.                        │
│                │ Serves static files without waking app server.   │
│                │ Rate limiting, compression, security headers.    │
├────────────────┼──────────────────────────────────────────────────┤
│ API Gateway    │ "I need auth, rate limiting, versioning."        │
│                │ Authentication before request reaches app.       │
│                │ Rate limiting per API key/user.                  │
│                │ Request/response transformation.                 │
│                │ API versioning, deprecation.                     │
├────────────────┼──────────────────────────────────────────────────┤
│ App Server     │ "Process the actual business logic."             │
│                │ Your FastAPI/Express/Koa code.                   │
│                │ Only cares about request → response.             │
└────────────────┴──────────────────────────────────────────────────┘
```

#### The power: add/remove layers without changing code

```
SCENARIO 1: Start simple, add layers as you grow

  Day 1 (prototype):
    Browser → Express on port 3000
    One server. No layers. Works fine for 10 users.
    
  Month 3 (growing):
    Browser → nginx → Express
    Added nginx for TLS, compression, static files.
    Express code: UNCHANGED.
    
  Month 6 (scaling):
    Browser → ALB → nginx (container 1) → Express
                  → nginx (container 2) → Express
                  → nginx (container 3) → Express
    Added ALB for load balancing. 3 containers.
    Express code: UNCHANGED.
    nginx config: UNCHANGED.
    
  Month 12 (global users):
    Browser → CloudFront → ALB → containers
    Added CDN for global caching.
    Express code: UNCHANGED.
    ALB config: UNCHANGED.

  EVERY layer added without touching application code.


SCENARIO 2: Swap a layer

  Before: ALB → nginx → uvicorn → FastAPI
  After:  ALB → uvicorn → FastAPI (removed nginx)
  
  FastAPI code: UNCHANGED.
  Client code: UNCHANGED.
  Just removed one intermediary.


SCENARIO 3: Add security layer

  Before: Browser → ALB → FastAPI
  After:  Browser → WAF → ALB → FastAPI
                    ^^^
                    Web Application Firewall
                    Blocks SQL injection, XSS, bot traffic
  
  FastAPI code: UNCHANGED.
  Client code: UNCHANGED.
  Security improved without touching any application code.
```


#### How layers stay transparent — the HTTP contract

```
WHY can layers be added without code changes?

  Because every layer speaks the SAME PROTOCOL: HTTP.

  ┌──────────┐ HTTP  ┌──────────┐ HTTP  ┌──────────┐ HTTP  ┌──────────┐
  │  Client  │──────→│   CDN    │──────→│   ALB    │──────→│  Server  │
  └──────────┘       └──────────┘       └──────────┘       └──────────┘

  Each layer:
    1. Receives an HTTP request
    2. Optionally modifies it (add headers, cache, redirect)
    3. Forwards to next layer (or responds from cache)
    4. Receives HTTP response from next layer
    5. Optionally modifies it (add headers, compress)
    6. Sends response back to previous layer


  The CONTRACT at each boundary is the same:
    "I give you an HTTP request, you give me an HTTP response."
  
  As long as this contract holds, any layer can be:
    - Added (insert CDN between client and server)
    - Removed (remove nginx, let ALB talk to app directly)
    - Replaced (swap nginx for Caddy or Envoy)
    - Duplicated (add multiple ALBs for multi-region)
```


#### Headers that layers add for transparency
```
Layers are "transparent" but often ADD headers
to pass information along:

  X-Forwarded-For: 203.0.113.50, 70.41.3.18
  ─────────────────────────────────────────────
  "Original client IP, then each proxy IP."
  
  Browser (203.0.113.50) → CDN (70.41.3.18) → ALB → Server
  
  Server sees: request from ALB's IP (10.0.1.50)
  But X-Forwarded-For tells it: real client is 203.0.113.50
  
  Without this header: server logs would show ALB's IP
  for ALL requests. Useless for analytics/security.


  X-Forwarded-Proto: https
  ─────────────────────────
  "Original request was HTTPS."
  
  Browser → HTTPS → ALB (terminates TLS) → HTTP → Server
  
  Server receives plain HTTP.
  But X-Forwarded-Proto says: "user connected via HTTPS."
  Important for: generating correct redirect URLs.


  X-Request-Id: abc-123-def-456
  ──────────────────────────────
  "Unique ID for this request, across all layers."
  
  ALB generates ID → passes to nginx → passes to FastAPI
  All layers log this ID.
  When debugging: search logs for "abc-123-def-456"
  → see the request's journey through every layer.


  X-Forwarded-Host: answer.astrazeneca.com
  ──────────────────────────────────────────
  "Original Host header from the client."
  
  Client sends: Host: answer.astrazeneca.com
  ALB routes to: container at 10.0.1.50:8000
  Server sees: Host: 10.0.1.50:8000 (internal)
  X-Forwarded-Host preserves the original.
```

#### TLS termination — a layer's most common job

```
"TLS termination" = the layer that DECRYPTS HTTPS.

  OPTION A: TLS at ALB (most common)
  ────────────────────────────────────

    Browser ══HTTPS══> ALB ──HTTP──> Container
             encrypted     unencrypted (private network)
             
    ALB holds the TLS certificate.
    ALB decrypts. Container receives plain HTTP.
    
    ✅ Container doesn't need certificate management
    ✅ CPU-intensive decryption offloaded from app
    ✅ Simple container setup
    ⚠️ Traffic between ALB and container is unencrypted
       (OK if within same VPC/private network)


  OPTION B: TLS at CDN + ALB
  ───────────────────────────

    Browser ══HTTPS══> CloudFront ══HTTPS══> ALB ──HTTP──> Container
             encrypted              encrypted    unencrypted
    
    Two TLS terminations.
    CloudFront decrypts, re-encrypts to ALB.
    ALB decrypts, sends plain HTTP to container.


  OPTION C: End-to-end TLS (high security)
  ───────────────────────���─────────────────

    Browser ══HTTPS══> ALB ══HTTPS══> Container
             encrypted      encrypted
    
    TLS all the way to the application.
    Container manages its own certificate.
    Required for: PCI compliance, healthcare data (sometimes).
    
    ⚠️ More complex. Certificate rotation on every container.


  Your app probably uses Option A or B:
    ALB terminates TLS. Internal traffic is plain HTTP.
    VPC security groups ensure only ALB can reach containers.
```

#### Load balancing algorithms — how ALB chooses
```
When ALB has 3 healthy containers, which gets the request?


  ROUND ROBIN (simplest):
  ───────────────────────
  
    Request 1 → Container A
    Request 2 → Container B
    Request 3 → Container C
    Request 4 → Container A  (cycle repeats)
    
    ✅ Simple, fair
    ⚠️ Doesn't account for container load
       (one might have a heavy search running)


  LEAST CONNECTIONS (smarter):
  ────────────────────────────
  
    Container A: 5 active connections
    Container B: 2 active connections
    Container C: 8 active connections
    
    Next request → Container B (fewest connections)
    
    ✅ Accounts for actual load
    ✅ Better for long-lived connections (SSE, WebSocket)
    
    Your SSE streams: one container could accumulate many
    SSE connections. Least connections sends new requests
    to less-loaded containers.


  WEIGHTED (manual control):
  ──────────────────────────
  
    Container A (powerful): weight 5
    Container B (small):    weight 1
    
    A gets 5× more traffic than B.
    Useful for: gradual rollouts, mixed instance sizes.


  ALB (your app) uses round robin by default
  within a target group, with slow start mode available.
```


#### Layered system enables zero-downtime deployments

```
This is one of the most PRACTICAL benefits:

  You need to deploy a new version. Users are active.

  WITHOUT layers:
    Stop server → deploy → start server
    During deployment: ALL users see errors. 💀


  WITH layers (rolling deployment):

    ALB → Container A (v1) ✅ serving traffic
        → Container B (v1) ✅ serving traffic
        → Container C (v1) ✅ serving traffic

    Step 1: Deploy v2 to Container A
      ALB health check: Container A failing (restarting)
      ALB removes Container A from rotation
      
      ALB → Container A (deploying...) ❌ no traffic
          → Container B (v1) ✅ gets more traffic
          → Container C (v1) ✅ gets more traffic
    
    Step 2: Container A healthy with v2
      ALB adds Container A back
      
      ALB → Container A (v2) ✅
          → Container B (v1) ✅
          → Container C (v1) ✅
    
    Step 3: Repeat for B, then C
      
      ALB → Container A (v2) ✅
          → Container B (v2) ✅
          → Container C (v2) ✅

    Users: never saw an error. Some got v1, some got v2,
    eventually all get v2. Zero downtime.

    Client code: UNCHANGED. Didn't know deployment happened.
```


#### The constraint: layers can't "skip"
```
REST says each layer can ONLY talk to the adjacent layer.

  ✅ CORRECT:
  
    Client → CDN → ALB → Server
    
    Client talks to CDN.
    CDN talks to ALB.
    ALB talks to Server.
    
    Client does NOT talk directly to Server.
    Client does NOT talk directly to ALB.


  ❌ VIOLATION:
  
    Client → CDN → ALB → Server
      │                    ↑
      └── direct call ─────┘
    
    Client bypasses CDN and ALB, calls server directly.
    This breaks the layered system.
    Server now needs to handle TLS, rate limiting, etc.
    All the benefits of intermediary layers are lost.


  WHY this rule exists:

    Each layer provides guarantees:
      CDN: caching, DDoS protection
      ALB: load balancing, health checks
      nginx: rate limiting, buffering
    
    If client skips a layer, those guarantees are lost.
    
    Real-world enforcement:
      Server is in PRIVATE subnet (no public IP).
      ONLY ALB can reach it (security group rules).
      Client literally CAN'T skip layers.
      The network topology enforces the constraint.
```

### Summary
```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  LAYERED SYSTEM means:                                               │
│                                                                      │
│    1. Intermediaries can exist between client and server             │
│    2. Each layer only knows about adjacent layers                    │
│    3. Layers are TRANSPARENT — same HTTP contract throughout         │
│    4. Add/remove/replace layers without changing application code    │
│                                                                      │
│  Each layer solves ONE concern:                                      │
│    DNS        → name resolution, geographic routing                  │
│    CDN        → caching, edge delivery, DDoS protection              │
│    WAF        → security filtering                                   │
│    ALB        → load distribution, health checks                     │
│    Proxy      → buffering, compression, rate limiting                │
│    App Server → business logic                                       │
│                                                                      │
│  Benefits:                                                           │
│    Performance  → CDN caching, compression, geographic routing       │
│    Scalability  → load balancing across N servers                    │
│    Security     → TLS termination, WAF, rate limiting                │
│    Reliability  → health checks, failover, zero-downtime deploys     │
│    Flexibility  → swap any layer without touching others             │
│                                                                      │
│  Mental model:                                                       │
│    HTTP is the universal contract between all layers.                │
│    Every layer receives HTTP and returns HTTP.                       │
│    This uniformity is what makes layers pluggable.                   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```
