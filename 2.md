## Process

`process` — глобальный объект Node.js

`process` доступен **глобально**, потому что он создаётся на этапе `bootstrap` — ещё до того, как твой код начнёт выполняться. 
`V8 isolate` инициализируется, создаётся `process object`, и только потом загружается твой `entry point`.

Тем не менее, можно импортировать явно (полезно для `tree-shaking` и явности):
```
import process from 'node:process';
```

`process` — это **интроспекция**: ты можешь узнать всё о текущем запущенном процессе:

#### Идентификация
```
process.pid        // 48251 — PID процесса (то что видно в `ps aux`)
process.ppid       // 48250 — PID родительского процесса
process.title      // 'node' — имя процесса (можно менять, видно в `top`)
```

#### Окружение
```
process.env        // { PATH: '...', HOME: '...', NODE_ENV: 'production', ... }
                   // объект с ВСЕМИ переменными окружения
                   // каждое значение — СТРОКА (даже если выглядит как число)

process.env.NODE_ENV   // 'production' | 'development' | undefined
process.env.PORT       // '3000' ← строка, не число!
```

#### Информация о запуске
```
process.argv       // ['/usr/bin/node', '/app/server.js', '--port', '3000']
process.execPath   // '/usr/bin/node' — абсолютный путь к бинарнику node
process.execArgv   // ['--max-old-space-size=4096'] — флаги для node (не для скрипта)
process.cwd()      // '/home/user/project' — текущая рабочая директория
```

#### Информация о платформе
```
process.platform   // 'linux' | 'darwin' | 'win32'
process.arch       // 'x64' | 'arm64'
process.version    // 'v20.11.0'
process.versions   // { node: '20.11.0', v8: '11.3.244.8', openssl: '3.0.12', ... }
```


### process — не только чтение информации, но и управление процессом:

#### Завершение
```
process.exit(0)    // немедленное завершение, exit code 0 (success)
process.exit(1)    // exit code 1 (failure)

process.exitCode = 1;  // установить код без немедленного завершения
                       // процесс завершится с этим кодом когда event loop опустеет
```

#### I/O потоки (stdin, stdout, stderr)

```
process.stdout.write('hello\n');     // fd 1
process.stderr.write('error!\n');    // fd 2

process.stdin.on('data', (chunk) => {   // fd 0
  console.log('Получил:', chunk.toString());
});
```

### process — это точка соприкосновения JS-кода с ОС:

```
Внешний мир                    process                     Твоя логика
─────────────────          ─────────────────           ─────────────────
Аргументы CLI      →    process.argv            →    Парсинг опций
Переменные окруж.  →    process.env             →    Конфигурация
Сигналы ОС         →    process.on('SIGTERM')   →    Graceful shutdown
stdin (pipe/tty)   →    process.stdin           →    Чтение ввода
                         process.stdout          ←    Вывод данных
                         process.stderr          ←    Вывод ошибок
                         process.exit()          →    Завершение с кодом
                         process.cwd()           →    Работа с путями
```

### Process Events — обработка фатальных ошибок


#### Почему process — это EventEmitter

```
const EventEmitter = require('events');
process instanceof EventEmitter  // true
```

`process` наследует от `EventEmitter` — это позволяет ядру Node.js и `libuv` уведомлять твой код 
о системных событиях (сигналы, ошибки, завершение) через знакомый паттерн `.on(event, listener)`.

Событий у `process` много, но два из них — последний рубеж обороны перед крахом программы.

### Механика обработки ошибок в Node.js — нормальный путь

```
// Уровень 1: try/catch — синхронный код
try {
  JSON.parse('invalid');
} catch (err) {
  // ошибка ПОЙМАНА — process живёт дальше
}

// Уровень 2: .catch() — промисы
fetch('/api')
  .then(res => res.json())
  .catch(err => {
    // rejection ПОЙМАН — process живёт дальше
  });

// Уровень 3: try/catch в async/await
async function load() {
  try {
    const data = await fs.promises.readFile('/missing');
  } catch (err) {
    // ошибка ПОЙМАНА — process живёт дальше
  }
}
```

❗Если ошибка поймана на любом из этих уровней — всё хорошо. 
Но если ни один обработчик не поймал — **ошибка «всплывает» до самого `process`**.

### `uncaughtException`

#### Когда возникает

Когда синхронный `throw` проходит через весь `call stack` и никто его не поймал:
```
function third()  { throw new Error('boom'); }
function second() { third(); }   // нет try/catch
function first()  { second(); }  // нет try/catch

first();  // нет try/catch
// Call stack размотался полностью → некому ловить → uncaughtException
```

#### Что происходит внутри V8 / Node.js

```
1. V8 выбрасывает исключение (throw)
2. V8 ищет ближайший catch в call stack (stack unwinding)
3. Не находит → исключение достигает boundary между V8 и Node.js core
4. Node.js core проверяет: есть ли listeners на process 'uncaughtException'?

   НЕТ listeners → печатает stack trace в stderr → process.exit(1)
   
   ЕСТЬ listener → вызывает его:
      process.emit('uncaughtException', error, origin)
```

```
// Без обработчика:
setTimeout(() => {
  throw new Error('async boom');  // callback выполняется вне try/catch
}, 100);

// Результат:
// /app/server.js:2
//   throw new Error('async boom');
//   ^
// Error: async boom
//     at Timeout._onTimeout (/app/server.js:2:9)
// 
// Node.js process exited with code 1
```


```
// С обработчиком:
process.on('uncaughtException', (error, origin) => {
  // origin = 'uncaughtException' | 'unhandledRejection'
  console.error(`[FATAL] ${origin}: ${error.message}`);
  console.error(error.stack);
  
  // Отправить в систему мониторинга (Sentry, Datadog, etc.)
  // НО: это best-effort — process может быть в broken state
  
  process.exit(1);
});
```

### Почему callback-ошибки «непойманные»

```
// Это НЕ поймает ошибку:
try {
  setTimeout(() => {
    throw new Error('boom');  // выполнится в ДРУГОМ тике event loop
  }, 100);
} catch (err) {
  // НИКОГДА не сработает
  // к моменту throw — try/catch уже давно завершился
}
```

```
Tick 1: try { setTimeout(fn, 100) } catch {...}  ← завершился, catch уже снят со стека
Tick 2: ...
Tick N: fn() → throw → call stack ПУСТ кроме fn → uncaughtException
```


### Практический production-шаблон
```
import process from 'node:process';

// Последний рубеж — только логирование и завершение
process.on('uncaughtException', (err, origin) => {
  process.stderr.write(`[FATAL] ${origin}: ${err.stack}\n`);
  process.exitCode = 1;
  // Даём время на flush (stdout может быть buffered в pipe)
  setTimeout(() => process.exit(1), 100).unref();
});

process.on('unhandledRejection', (reason) => {
  // Преобразуем в uncaughtException для единообразной обработки
  throw reason;
});
```

### Почему НЕЛЬЗЯ продолжать работу после `uncaughtException`

```
process.on('uncaughtException', (err) => {
  console.error(err);
  // НЕ вызываем process.exit() — пытаемся продолжить...
});
```

```
1. НЕИЗВЕСТНОЕ СОСТОЯНИЕ
   Исключение прервало выполнение функции на ПРОИЗВОЛЬНОЙ строке.
   Часть операций выполнена, часть — нет:
   
   function transferMoney(from, to, amount) {
     from.balance -= amount;    // ← выполнилось
     if (amount > 10000) audit(amount);  // ← throw здесь
     to.balance += amount;      // ← НЕ выполнилось!
   }
   // Деньги списаны, но не зачислены. Данные inconsistent.

2. УТЕЧКА РЕСУРСОВ
   - Открытые file descriptors не закрыты
   - Database transactions не откачены (не ROLLBACK)
   - Mutex/lock захвачен но не отпущен
   - Сетевые соединения в промежуточном состоянии

3. ПОВРЕЖДЁННЫЙ INTERNAL STATE
   - Event loop может быть в некорректном состоянии
   - libuv handles могут быть полузакрыты
   - V8 heap может содержать невалидные ссылки
```

### Правильный паттерн — «crash and restart»

```
process.on('uncaughtException', (err) => {
  // 1. Логировать (best-effort)
  logger.fatal({ err }, 'Uncaught exception — shutting down');
  
  // 2. Попытаться flush логов (sync!)
  try { fs.writeFileSync('/var/log/app/crash.log', err.stack); } catch {}
  
  // 3. НЕМЕДЛЕННО завершить
  process.exit(1);
  
  // 4. Внешний supervisor перезапустит процесс:
  //    - systemd (Restart=always)
  //    - Docker (restart: unless-stopped)  
  //    - Kubernetes (restartPolicy: Always)
  //    - PM2 (автоматический restart)
});
```

### Nodejs VS Browser: Почему в Node.js обработка ошибок критичнее
Браузер не падает при uncaught exception — он просто логирует ошибку. 

```
БРАУЗЕР                              NODE.JS
────────────────────                 ────────────────────
1 пользователь = 1 вкладка          1 процесс = 1000 пользователей
                                     
Ошибка → сломается у ОДНОГО         Ошибка → сервер ПАДАЕТ
человека, он перезагрузит            → ВСЕ клиенты отключены
страницу                             → нужен restart

UI может быть частично рабочим       Процесс мёртв полностью

Worst case: пользователь             Worst case: потеря данных,
обновит страницу (Ctrl+R)            downtime, потерянные транзакции
```
