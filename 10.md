```
Server Push НЕ значит "сервер подключается к браузеру".

Сервер отправляет ДОПОЛНИТЕЛЬНЫЕ данные
по ТОМУ ЖЕ соединению, которое БРАУЗЕР открыл.

Браузер по-прежнему инициировал socket.
Сервер просто пишет в него БОЛЬШЕ чем просили.
```

#### HTTP/1.1 — строгий "запрос-ответ"
```
Браузер                          Сервер
───────                          ──────

connect(server:443) ──────→      accept()

"GET /index.html"   ──────→     
                    ←──────      "вот index.html"

Браузер парсит HTML, видит <link href="style.css">

"GET /style.css"    ──────→
                    ←──────      "вот style.css"

Браузер видит <script src="app.js">

"GET /app.js"       ──────→
                    ←──────      "вот app.js"


3 запроса, 3 ответа. Строго по очереди.
Сервер ЗНАЕТ что после index.html понадобятся css и js,
но ЖДЁТ пока браузер попросит.
```

#### HTTP/2 Server Push — сервер отправляет заранее

```
Браузер                          Сервер
───────                          ──────

connect(server:443) ──────→      accept()
                                 
                                 Одно TCP соединение.
                                 Но HTTP/2 мультиплексирует
                                 НЕСКОЛЬКО потоков внутри него.

"GET /index.html"   ──────→     
                                 Сервер думает:
                                 "Ему точно нужны css и js,
                                  отправлю сразу не дожидаясь"

                    ←──────      PUSH_PROMISE: "я пришлю style.css"
                    ←──────      PUSH_PROMISE: "я пришлю app.js"
                    ←──────      вот index.html (stream 1)
                    ←──────      вот style.css  (stream 2)
                    ←──────      вот app.js     (stream 3)


1 запрос от браузера → 3 ответа от сервера.
Браузер НЕ просил css и js.
Сервер отправил их САМ через ТО ЖЕ соединение.
```

#### Socket при этом НЕ меняется
```
                    ОДИН TCP socket (браузер инициировал)
                    ════════════════════════════════════
                    
Браузер (fd=3)  ◄══════════════════════════►  Сервер (fd=6)
   client socket      TCP соединение           server socket
   connect()                                   accept()


Внутри этого ОДНОГО соединения HTTP/2 создаёт ПОТОКИ (streams):

┌─── TCP Socket (одно соединение) ────────────────────────┐
│                                                          │
│   Stream 1: GET /index.html  →  ← ответ HTML            │
│   Stream 2: (push)              ← PUSH_PROMISE + CSS    │
│   Stream 3: (push)              ← PUSH_PROMISE + JS     │
│   Stream 4: GET /api/data    →  ← ответ JSON            │
│                                                          │
│   Все streams внутри ОДНОГО TCP соединения.              │
│   Мультиплексирование: данные чередуются.                │
│                                                          │
└──────────────────────────────────────────────────────────┘

Новых socket-ов НЕ создаётся.
Сервер НЕ подключается к браузеру.
Сервер пишет write(fd=6, ...) — в тот же socket.
```

#### WebSocket?
```
Тот же принцип:

1. БРАУЗЕР инициирует соединение (client socket, connect)
2. Просит "давай перейдём на WebSocket протокол"
3. Сервер соглашается (upgrade)
4. Дальше ОБА могут писать в socket В ЛЮБОЙ МОМЕНТ

Браузер                          Сервер
───────                          ──────

connect(server:443) ──────→      accept()
"Upgrade: websocket" ─────→
                     ←─────      "101 Switching Protocols"

                                 Теперь ДВУСТОРОННИЙ канал:

"привет"            ──────→
                    ←──────      "привет!"
                    ←──────      "новое сообщение в чате"
                    ←──────      "пользователь онлайн"
"ок"                ──────→


Socket по-прежнему тот же.
Браузер по-прежнему инициировал connect().
Просто ПРОТОКОЛ позволяет серверу писать когда хочет.
```

```
Socket (TCP):
  Двусторонний канал.
  Оба конца могут писать/читать в любой момент.
  Это то как работает ЛЮБОЕ сетевое общение на уровне ОС.

HTTP (что было в браузере):
  Однонаправленный запрос-ответ.
  Клиент спросил → сервер ответил → всё, молчим.
  Это ОГРАНИЧЕНИЕ поверх socket.

WebSocket:
  Вернул браузеру поведение НАСТОЯЩЕГО socket-а.
  Отсюда и название.
```

#### Проблема которую решали

```
TCP Socket (за пределами браузера):
─────────────────────────────────────

  Программа A                Программа B
       │                          │
       │←── пишу когда хочу ────→ │
       │←── читаю когда хочу ──→  │
       │                          │
  Постоянное соединение. Оба равноправны.
  Так работают: онлайн-игры, чаты, биржевые терминалы.


HTTP в браузере (до WebSocket):
─────────────────────────────────────

  Браузер                    Сервер
       │                       │
       │── GET /messages ──→   │
       │                  ←──  │  ответ
       │                       │
       │   ...тишина...        │
       │                       │
       │── GET /messages ──→   │  опять спрашиваем
       │                  ←──  │  ответ
       │                       │
       │   ...тишина...        │

  Браузер не может просто СЛУШАТЬ.
  Сервер не может просто НАПИСАТЬ.
  Каждый раз новый запрос. Неэффективно.
```

#### Что хотели разработчики
```
Они хотели дать браузеру ТО ЖЕ поведение
что имеет обычный TCP socket:

  TCP Socket:                WebSocket:
  ──────────                 ──────────
  connect()                  new WebSocket(url)
  write(data)                ws.send(data)
  on('data', read)           ws.onmessage = (msg) => {}
  close()                    ws.close()

  Двусторонний               Двусторонний
  Постоянный                 Постоянный
  Пишу когда хочу            Пишу когда хочу

Почти ИДЕНТИЧНЫЙ интерфейс.
Поэтому и назвали "WebSocket" — socket который работает в web.
```

#### Почему нельзя было дать браузеру настоящий TCP socket?

```
Настоящий TCP socket в браузере — это ДЫРА в безопасности:

  const s = net.connect('192.168.1.1', 22);   // SSH к роутеру
  const s = net.connect('10.0.0.5', 5432);    // PostgreSQL в сети
  const s = net.connect('127.0.0.1', 6379);   // Redis на localhost

  Любой сайт мог бы:
    ─ сканировать порты локальной сети
    ─ подключаться к внутренним сервисам
    ─ отправлять произвольные TCP пакеты

  ❌ Категорически нельзя.


WebSocket — БЕЗОПАСНАЯ версия socket-а:
  
  ✅ Работает только поверх HTTP/HTTPS (порт 80/443)
  ✅ Начинается с HTTP handshake (проходит через прокси/файрволы)
  ✅ Сервер должен ЯВНО согласиться (Upgrade: websocket)
  ✅ Подчиняется CORS политикам
  ✅ Нельзя подключиться к произвольному TCP порту
```

#### Как WebSocket становится "socket-ом"
```
Шаг 1: Обычный HTTP запрос (рукопожатие)
──────────────────────────────────────────

  Браузер → Сервер:
    GET /chat HTTP/1.1
    Upgrade: websocket              ← "Хочу перейти на WebSocket"
    Connection: Upgrade
    Sec-WebSocket-Key: dGhlIHN...   ← ключ для проверки

  Сервер → Браузер:
    HTTP/1.1 101 Switching Protocols  ← "Ок, переключаемся"
    Upgrade: websocket
    Sec-WebSocket-Accept: s3pPL...


Шаг 2: TCP соединение ОСТАЁТСЯ, протокол МЕНЯЕТСЯ
──────────────────────────────────────────────────

  До Upgrade:
  ┌─── TCP Socket ───────────────────────┐
  │  Протокол: HTTP (запрос-ответ)       │
  │  Ограничение: клиент спросил →       │
  │               сервер ответил → тишина│
  └──────────────────────────────────────┘

  После Upgrade:
  ┌─── TCP Socket (ТОТ ЖЕ fd!) ─────────┐
  │  Протокол: WebSocket (двусторонний)  │
  │  Оба пишут когда хотят               │
  │  Постоянное соединение               │
  │  Поведение = как настоящий socket    │
  └──────────────────────────────────────┘

  Socket тот же. Протокол поверх него — другой.
```

#### Сравнение названий

```
TCP Socket:
  "Socket" — оригинальный сетевой примитив ОС (1983, BSD)
  Двусторонний канал между двумя программами
  Любой протокол, любой порт, полный контроль

WebSocket:
  "Web" + "Socket" — socket-подобное поведение В БРАУЗЕРЕ
  Двусторонний канал между браузером и сервером
  Ограничен: только поверх HTTP, только с согласия сервера

  Назван "socket" потому что ВЕДЁТ СЕБЯ как socket:
    ─ постоянное соединение
    ─ двусторонняя передача
    ─ send/receive в любой момент
```
