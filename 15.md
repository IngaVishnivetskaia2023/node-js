## HTTP Caching

#### The mental model: why caching exists

```
WITHOUT caching:

  Browser                              Server
    │                                     │
    │── GET /api/users/123 ──────────────→│  query DB, build response
    │←── 200 OK { name: "Anna" }  ────────│  100ms
    │                                     │
    │  ... 5 seconds later ...            │
    │                                     │
    │── GET /api/users/123 ──────────────→│  query DB again, same result
    │←── 200 OK { name: "Anna" }  ────────│  100ms
    │                                     │
    │  ... 5 seconds later ...            │
    │                                     │
    │── GET /api/users/123 ──────────────→│  query DB again, same result
    │←── 200 OK { name: "Anna" }  ────────│  100ms

  Same question, same answer, 3 times.
  Wasted: server CPU, database queries, network bandwidth, user's time.


WITH caching:

  Browser                              Server
    │                                     │
    │── GET /api/users/123 ──────────────→│  query DB, build response
    │←── 200 OK { name: "Anna" }   ───────│  100ms
    │   Cache-Control: max-age=60         │
    │                                     │
    │  ... 5 seconds later ...            │
    │                                     │
    │── GET /api/users/123                │
    │  Browser: "I have this cached.      │
    │   max-age=60, only 5s passed."      │
    │  NO REQUEST SENT. 0ms. ✅          │
    │                                     │
    │  ... 5 seconds later ...            │
    │                                     │
    │── GET /api/users/123                │
    │  Browser: "Still cached. 10s < 60s" │
    │  NO REQUEST SENT. 0ms. ✅           │

  2 requests eliminated entirely.
  Zero network. Zero server load. Instant response.
```

#### The two questions of caching

```
Every caching decision answers TWO questions:

  QUESTION 1: "Can I use my cached copy WITHOUT asking the server?"
  ─────────────────────────────────────────────────────────────────
  
  This is FRESHNESS. Controlled by Cache-Control and max-age.
  
  If cached copy is FRESH → use it immediately. No network request.
  If cached copy is STALE → go to Question 2.


  QUESTION 2: "My cache is stale. Has the resource actually changed?"
  ──────────────────────────────────────────────────────────────────
  
  This is VALIDATION. Controlled by ETag and Last-Modified.
  
  Browser asks server: "Here's what I have. Is it still valid?"
  Server says: 304 Not Modified (use your cache) — saves bandwidth
           or: 200 OK + new body (here's the updated version)


  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  Request arrives at browser cache:                         │
  │                                                            │
  │  Is there a cached copy?                                   │
  │    NO  → send request to server (normal flow)              │
  │    YES → Is it fresh? (max-age not expired?)               │
  │            YES → use cache immediately (NO request) ⚡    │
  │            NO  → validate with server (conditional req)    │
  │                    Server says 304? → use cache            │
  │                    Server says 200? → use new response     │
  │                                                            │
  └────────────────────────────────────────────────────────────┘
```

#### Cache-Control header — every directive explained

```
Cache-Control is the PRIMARY caching header.
Sent by the SERVER in the response.
Tells browser (and intermediate caches) what to do.


  Cache-Control: max-age=3600
  ────────────────────────────
  
  "This response is valid for 3600 seconds (1 hour)."
  
  Browser receives response at 10:00 AM.
  Until 11:00 AM: use cached copy, don't ask server.
  After 11:00 AM: cache is stale, must revalidate.
  
  Timeline:
    10:00  GET /api/users/123 → 200 OK (from server, cached)
    10:15  GET /api/users/123 → 200 OK (from cache, instant) ⚡
    10:30  GET /api/users/123 → 200 OK (from cache, instant) ⚡
    10:59  GET /api/users/123 → 200 OK (from cache, instant) ⚡
    11:01  GET /api/users/123 → stale, must revalidate with server


  Cache-Control: no-cache
  ───────────────────────
  
  ⚠️ MISLEADING NAME. Does NOT mean "don't cache."
  
  It means: "You CAN store it, but ALWAYS ask the server
  before using it." (Always revalidate.)
  
  Browser stores response in cache.
  On every request: sends conditional request to server.
  Server says 304? Use cache. Says 200? Use new response.
  
  ALWAYS makes a network request, but potentially saves bandwidth
  (304 has no body).
  
  This is what index.html should use:
    Always check if a new version exists,
    but if it hasn't changed, use cache (304, no body transfer).


  Cache-Control: no-store
  ───────────────────────
  
  "Do NOT store this response. At all. Anywhere. Ever."
  
  Not in browser cache.
  Not in CDN cache.
  Not on disk.
  
  Every request goes to the server. Full response every time.
  
  Use for: sensitive data (bank balances, personal info, auth tokens)
  Your app: search results with patient data → no-store.


  Cache-Control: public
  ─────────────────────
  
  "ANY cache can store this — browser, CDN, proxy, ISP cache."
  
  Use for: static files, public API responses.
  Your Vite bundles: public (anyone can cache main.js).


  Cache-Control: private
  ──────────────────────
  
  "Only the USER'S BROWSER can cache this. No shared caches."
  
  CDN → NO. Proxy → NO. Browser → YES.
  
  Use for: user-specific data.
  GET /api/v2/user-settings → private (Anna's settings ≠ Bob's settings)
  If CDN cached it: Bob might see Anna's settings.


  Cache-Control: immutable
  ────────────────────────
  
  "This resource will NEVER change. Don't even revalidate."
  
  Even when user hits Refresh button, browser won't recheck.
  Normal max-age: refresh button triggers revalidation.
  With immutable: refresh button still uses cache.
  
  ONLY use with content-hashed filenames:
    /assets/index-a1b2c3.js → immutable ✅ (hash changes if content changes)
    /api/users/123          → immutable ❌ (data can change!)


  Cache-Control: s-maxage=3600
  ────────────────────────────
  
  Like max-age, but ONLY for shared caches (CDN, proxy).
  Browser ignores s-maxage and uses max-age.
  
  Cache-Control: max-age=60, s-maxage=3600
  "Browser: cache for 60 seconds."
  "CDN: cache for 1 hour."
  
  Useful when you want CDN to cache longer than browsers.


  Cache-Control: must-revalidate
  ──────────────────────────────
  
  "Once stale, you MUST revalidate. Don't serve stale content."
  
  Without must-revalidate: browser MIGHT serve stale content
  if server is unreachable (offline mode, network error).
  
  With must-revalidate: stale content → error, not stale cache.


  COMBINED EXAMPLE (your Vite bundles):
  
  Cache-Control: public, max-age=31536000, immutable
                 ^^^^^^  ^^^^^^^^^^^^^^^^  ^^^^^^^^^
                 any cache  1 year          never changes
  
  "Cache everywhere. For 1 year. Content is permanent.
   Don't even revalidate. If content changes, URL changes."
```

#### ETag — version fingerprint

```
ETag = "Entity Tag" — a unique identifier for a specific VERSION
of a resource.

  Think of it like a git commit hash for an HTTP response.
  Same content = same ETag. Different content = different ETag.


HOW IT WORKS:

  Step 1: First request — server sends ETag

    Client: GET /api/users/123
    
    Server: 200 OK
            ETag: "a1b2c3d4"
            Content-Type: application/json
            
            {"name":"Anna","age":30}
    
    Browser stores: response + ETag "a1b2c3d4"


  Step 2: Later request — client sends ETag back

    Client: GET /api/users/123
            If-None-Match: "a1b2c3d4"    ← "I have this version"
    
    Server checks: current version ETag = "a1b2c3d4"?
    

  Step 3a: NOT CHANGED — 304

    Server: 304 Not Modified              ← NO BODY sent
            ETag: "a1b2c3d4"
    
    Browser: uses cached response. Saved bandwidth ✅
    
    What was saved:
      Without ETag: 200 OK + full JSON body (maybe 50KB)
      With ETag:    304 Not Modified (0 bytes body)


  Step 3b: CHANGED — 200 with new data

    Server: 200 OK
            ETag: "e5f6g7h8"             ← NEW ETag
            
            {"name":"Anna","age":31}      ← updated data
    
    Browser: replaces cached response with new one.


VISUAL:

  Request 1 (cache empty):
  ┌──────────┐  GET /user/123   ┌──────────┐
  │  Client  │ ───────────────→ │  Server  │
  │          │ ←─────────────── │          │
  │  cache:  │  200 OK          │  DB:     │
  │  empty   │  ETag: "a1b2"    │  Anna,30 │
  │          │  {Anna, 30}      │          │
  │          │                  │          │
  │  cache:  │                  │          │
  │  "a1b2"  │                  │          │
  │  Anna,30 │                  │          │
  └──────────┘                  └──────────┘

  Request 2 (data unchanged):
  ┌──────────┐  GET /user/123   ┌──────────┐
  │  Client  │  If-None-Match:  │  Server  │
  │          │  "a1b2"          │          │
  │          │ ───────────────→ │          │
  │          │ ←─────────────── │  check:  │
  │          │  304 Not Modified│  "a1b2"  │
  │          │  (no body!)      │  match!  │
  │          │                  │          │
  │  use     │                  │          │
  │ cache ✅ │                  │          │
  └──────────┘                  └──────────┘

  Request 3 (data changed):
  ┌──────────┐  GET /user/123   ┌──────────┐
  │  Client  │  If-None-Match:  │  Server  │
  │          │  "a1b2"          │          │
  │          │ ───────────────→ │          │
  │          │ ←─────────────── │  check:  │
  │          │  200 OK          │  "c3d4"  │
  │          │  ETag: "c3d4"    │  no match│
  │          │  {Anna, 31}      │  send new│
  │          │                  │          │
  │  update  │                  │          │
  │  cache   │                  │          │
  └──────────┘                  └──────────┘
```

#### How ETags are generated

```
STRONG ETag (exact byte-for-byte match):

  ETag: "a1b2c3d4"
  
  Generated by hashing the response body:
    const crypto = require('crypto');
    const body = JSON.stringify(data);
    const etag = crypto.createHash('md5').update(body).digest('hex');
    // or simply a version number from database
    
  Two responses with identical bytes → same ETag.
  Even one byte different → different ETag.


WEAK ETag (semantically equivalent):

  ETag: W/"a1b2c3d4"
         ^^
         W/ prefix means "weak"
  
  "These resources are equivalent, but not byte-identical."
  
  Example: same JSON data but different whitespace formatting.
  { "name": "Anna" }  vs  {"name":"Anna"}
  Different bytes. Same meaning. Same weak ETag.
  
  
  In practice:
    Strong ETag: hash of response body (most common)
    Weak ETag: database updated_at timestamp or version number
```


#### Last-Modified — time-based validation

```
Same concept as ETag, but uses timestamps instead of hashes.

  Step 1: Server sends Last-Modified
  
    Server: 200 OK
            Last-Modified: Wed, 15 Jan 2025 10:30:00 GMT
            
            {"name":"Anna","age":30}


  Step 2: Client sends it back
  
    Client: GET /api/users/123
            If-Modified-Since: Wed, 15 Jan 2025 10:30:00 GMT


  Step 3: Server compares
  
    Resource last changed at 10:30:00.
    Client has version from 10:30:00.
    Same? → 304 Not Modified.
    Resource changed at 11:00:00? → 200 OK + new body.


  ETag vs Last-Modified:
  ┌─────────────────────┬───────────────────┬───────────────────┐
  │                     │ ETag              │ Last-Modified     │
  ├─────────────────────┼───────────────────┼───────────────────┤
  │ Precision           │ Exact (hash)      │ 1-second          │
  │                     │                   │ (can't detect     │
  │                     │                   │  sub-second       │
  │                     │                   │  changes)         │
  ├─────────────────────┼───────────────────┼───────────────────┤
  │ Client sends        │ If-None-Match     │ If-Modified-Since │
  ├���────────────────┼───────────────────┼───────────────────┤
  │ Server computes     │ Hash of content   │ File/DB timestamp │
  ├─────────────────────┼───────────────────┼───────────────────┤
  │ Multiple changes    │ Detects all       │ Misses if within  │
  │ per second          │                   │ same second       │
  ├─────────────────────┼───────────────────┼───────────────────┤
  │ Use when            │ API responses,    │ Static files,     │
  │                     │ dynamic content   │ simple resources  │
  └─────────────────────┴───────────────────┴───────────────────┘

  If BOTH are present, ETag takes priority.
  Most modern APIs use ETag. Last-Modified is simpler but less precise.
```

#### Where caches live — the caching layers
```
Response travels through MULTIPLE caches:

  Server → CDN → Corporate Proxy → Browser
           ↑          ↑               ↑
        shared     shared          private
        cache      cache           cache


  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │  BROWSER CACHE (private):                                   │
  │    Stores responses for this specific user.                 │
  │    Cache-Control: private → stored here only.               │
  │    Location: disk or memory on user's machine.              │
  │                                                              │
  │  CDN CACHE (shared — CloudFront, Cloudflare):               │
  │    Stores responses for ALL users.                          │
  │    Cache-Control: public → stored here.                     │
  │    Location: edge servers worldwide.                        │
  │    ⚠️ Careful: user-specific data must be private!          │
  │                                                              │
  │  PROXY CACHE (shared — corporate proxy, ISP):               │
  │    Between user and internet.                               │
  │    Your AstraZeneca corporate network likely has one.        │
  │    Can cache public responses.                              │
  │                                                              │
  │  APPLICATION CACHE (Redis, in-memory):                      │
  │    YOUR code caches at application level.                   │
  │    Not HTTP caching — but serves same purpose.              │
  │    Your app: Redis caches search results.                   │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘


  Cache-Control: public, max-age=3600
    → cached in: browser ✅, CDN ✅, proxy ✅

  Cache-Control: private, max-age=3600  
    → cached in: browser ✅, CDN ❌, proxy ❌

  Cache-Control: no-store
    → cached in: browser ❌, CDN ❌, proxy ❌
```

#### Cache invalidation — the hard problem
```
  "There are only two hard things in Computer Science:
   cache invalidation and naming things."
   — Phil Karlton


THE PROBLEM:

  Server cached response: { name: "Anna", age: 30 }
  Cache-Control: max-age=3600 (1 hour)
  
  At minute 5: Anna updates her age to 31.
  Server now has: { name: "Anna", age: 31 }
  
  But cache still has: { name: "Anna", age: 30 }
  For the next 55 minutes, users see STALE DATA.

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Timeline:                                               │
  │                                                          │
  │  0:00  Response cached (age: 30, max-age: 3600)         │
  │  0:05  Data changes in DB (age: 31)                     │
  │  0:05  Cache still says age: 30 ← STALE                │
  │  0:30  Cache still says age: 30 ← STALE                │
  │  0:59  Cache still says age: 30 ← STALE                │
  │  1:00  Cache expires, revalidates, gets age: 31 ✅       │
  │                                                          │
  │  Users saw wrong data for 55 minutes.                   │
  │                                                          │
  └──────────────────────────────────────────────────────────┘


STRATEGIES TO HANDLE THIS:

  Strategy 1: Short max-age
  ─────────────────────────
  
    Cache-Control: max-age=10
    
    Stale for at most 10 seconds.
    But: more requests to server (less caching benefit).
    
    Trade-off: freshness vs performance.


  Strategy 2: no-cache (always revalidate)
  ─────────────────────────────────────────
  
    Cache-Control: no-cache
    ETag: "v1"
    
    Every request asks server: "Has it changed?"
    Server: 304 (not changed) or 200 (new data).
    
    Always fresh. But always makes a network request.
    Saves bandwidth (304 has no body), not round trips.


  Strategy 3: Content-hashed URLs (Vite approach)
  ────────────────────────────────────────────────
  
    /assets/index-a1b2c3.js → Cache-Control: immutable, max-age=31536000
    
    Content changes? URL changes:
    /assets/index-x9y8z7.js → different file, different cache entry
    
    Old URL: cached forever (nobody requests it anymore)
    New URL: fresh download (never been cached before)
    
    ZERO stale data. ZERO revalidation. Best of both worlds.
    But: only works for files where you control the URL.
    Can't do this with /api/users/123 (URL is fixed).


  Strategy 4: Cache busting via query string
  ───────────────────────────────────────────
  
    /api/config?v=1   → cached
    /api/config?v=2   → new cache entry (different URL)
    
    Simple but crude. Some CDNs ignore query strings.
    Content-hashed filenames are better.


  Strategy 5: CDN purge (active invalidation)
  ────────────────────────────────────────────
  
    Data changes → API tells CDN: "delete cache for /api/users/123"
    CloudFront: invalidation API.
    
    Fast but complex. Must track what to invalidate.
    Can't purge browser caches (only CDN/proxy).
```

#### Caching in Node.js — implementation
```
import http from 'http';
import crypto from 'crypto';

const server = http.createServer((req, res) => {
  
  // ─── STATIC FILE: cache forever (content-hashed) ──────────
  
  if (req.url.startsWith('/assets/')) {
    
    res.writeHead(200, {
      'Content-Type': 'application/javascript',
      'Cache-Control': 'public, max-age=31536000, immutable',
      //                ^^^^^^  ^^^^^^^^^^^^^^^^  ^^^^^^^^^
      //                CDN ok  1 year            never recheck
    });
    res.end(fileContent);
    return;
  }
  
  
  // ─── HTML PAGE: always revalidate ──────────────────────────
  
  if (req.url === '/' || req.url === '/index.html') {
    
    res.writeHead(200, {
      'Content-Type': 'text/html',
      'Cache-Control': 'no-cache',
      //                ^^^^^^^^
      //                store it, but always ask server first
    });
    res.end(htmlContent);
    return;
  }
  
  
  // ─── API: ETag-based caching ───────────────────────────────
  
  if (req.url === '/api/users/123') {
    
    const data = { name: 'Anna', age: 30 };
    const body = JSON.stringify(data);
    
    // Generate ETag from content
    const etag = crypto
      .createHash('md5')
      .update(body)
      .digest('hex');
    
    // Check if client has current version
    const clientEtag = req.headers['if-none-match'];
    
    if (clientEtag === etag) {
      // Client's cached version is current
      res.writeHead(304, {
        'ETag': etag,
        // NO body sent. Saves bandwidth.
      });
      res.end();
      return;
    }
    
    // Client doesn't have it, or has old version
    res.writeHead(200, {
      'Content-Type': 'application/json',
      'Cache-Control': 'private, max-age=60',
      //                ^^^^^^^  ^^^^^^^^^^^
      //                browser only (user-specific)
      //                fresh for 60 seconds
      'ETag': etag,
    });
    res.end(body);
    return;
  }
  
  
  // ─── SENSITIVE DATA: never cache ───────────────────────────
  
  if (req.url === '/api/auth/token') {
    
    res.writeHead(200, {
      'Content-Type': 'application/json',
      'Cache-Control': 'no-store',
      //                ^^^^^^^^
      //                do not store anywhere, ever
      'Pragma': 'no-cache',
      //        ^^^^^^^^
      //        HTTP/1.0 backward compatibility
    });
    res.end(JSON.stringify({ token: 'secret' }));
    return;
  }
});
```

### Complete decision tree
```
  "What Cache-Control should I use?"

  Is the response user-specific (auth-dependent)?
  │
  ├── YES: contains personal/sensitive data?
  │   │
  │   ├── YES (tokens, passwords, financial)
  │   │     → Cache-Control: no-store
  │   │       "Never store this anywhere"
  │   │
  │   └── NO (user preferences, profile, dashboard)
  │         → Cache-Control: private, max-age=60
  │           "Browser cache only, recheck every 60s"
  │           + ETag for validation
  │
  └── NO: same for all users
      │
      ├── Content changes frequently? (API responses)
      │   │
      │   ├── Must be real-time? (stock prices, live scores)
      │   │     → Cache-Control: no-cache
      │   │       "Always revalidate" + ETag
      │   │
      │   └── Slight staleness OK? (blog posts, product listings)
      │         → Cache-Control: public, max-age=300, s-maxage=3600
      │           "Browser: 5 min. CDN: 1 hour." + ETag
      │
      └── Content is permanent? (static files, builds)
          │
          ├── URL contains content hash?
          │   (index-a1b2c3.js, vendor-d4e5f6.js)
          │     → Cache-Control: public, max-age=31536000, immutable
          │       "Cache forever. URL changes when content changes."
          │
          └── URL is fixed?
              (index.html, manifest.json)
                → Cache-Control: no-cache
                  "Always check for new version." + ETag

```

### Summary

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  FRESHNESS (avoid requests entirely):                                │
│    Cache-Control: max-age=N     → use cache for N seconds            │
│    Cache-Control: immutable     → never recheck, even on refresh     │
│    Cache-Control: no-cache      → always recheck (but can cache)     │
│    Cache-Control: no-store      → never cache at all                 │
│                                                                      │
│  SCOPE (who can cache):                                              │
│    public   → browser, CDN, proxy (safe for all users)               │
│    private  → browser only (user-specific data)                      │
│    s-maxage → CDN/proxy TTL (independent from browser TTL)           │
│                                                                      │
│  VALIDATION (is cached copy still valid?):                           │
│    ETag + If-None-Match         → hash-based, precise                │
│    Last-Modified + If-Modified-Since → time-based, 1s precision      │
│    Server responds: 304 (use cache) or 200 (new data)                │
│                                                                      │
│  INVALIDATION (the hard problem):                                    │
│    Content-hashed URLs  → best (URL changes when content changes)    │
│    Short max-age        → simple (accept some staleness)             │
│    CDN purge            → active (complex but immediate)             │
│    no-cache + ETag      → always validate (safe but slower)          │
│                                                                      │
│  MENTAL MODEL:                                                       │
│    Caching = trading FRESHNESS for SPEED.                            │
│    More caching = faster but potentially stale.                      │
│    Less caching = always fresh but slower.                           │
│    Content-hashed URLs = both fast AND fresh (the ideal).            │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```
