#### Why frontend NEEDS a bundler

```
THE FUNDAMENTAL PROBLEM:

  Your React app:
  
    src/
    ├── App.jsx                    import React from 'react'
    ├── components/
    │   ├── SearchBar.jsx          import { useState } from 'react'
    │   ├── ResultsList.jsx        import axios from 'axios'
    │   └── StatusBadge.jsx        import clsx from 'clsx'
    ├── hooks/
    │   └── useSearch.js           import { useQuery } from 'react-query'
    └── utils/
        └── api.js                 import axios from 'axios'
  
  
  Problems the BROWSER can't solve:

    1. IMPORTS DON'T WORK (historically)
       import React from 'react'
       Browser: "What is 'react'? That's not a URL.
                 I need: import React from '/node_modules/react/index.js'
                 Actually that file imports 15 other files...
                 which import 40 more files...
                 which import 200 more files..."
       
       react alone = ~300 files in node_modules.
       300 HTTP requests to load ONE dependency. Unusable.

    2. JSX IS NOT JAVASCRIPT
       <SearchBar query={query} />
       Browser: "Syntax error. What is < doing here?"
       
       JSX must be TRANSFORMED to:
       React.createElement(SearchBar, { query: query })

    3. TYPESCRIPT IS NOT JAVASCRIPT
       function search(query: string): Promise<Result[]>
       Browser: "What is : string? Syntax error."

    4. CSS MODULES, SASS, TAILWIND
       import styles from './SearchBar.module.css'
       Browser: "Can't import CSS as a JavaScript object."

    5. ENVIRONMENT VARIABLES
       import.meta.env.VITE_API_URL
       Browser: "What is this? I don't have env vars."

    6. 500 FILES = 500 HTTP REQUESTS
       Even with HTTP/2, loading 500 separate files is slow.


  VITE SOLVES ALL OF THIS:

    500 source files          →  3 output files
    JSX syntax                →  React.createElement calls
    TypeScript                →  plain JavaScript
    import 'react'            →  bundled into vendor.js
    CSS modules               →  bundled into style.css
    env variables             →  inlined as strings
    
    src/ (500 files)    →  dist/
                            ├── index.html
                            ├── assets/
                            │   ├── index-a1b2c3.js    (your code)
                            │   ├── vendor-d4e5f6.js   (dependencies)
                            │   └── index-g7h8i9.css   (all styles)
                            
    Browser loads 3 files instead of 500. Everything is valid JS.
```

#### Why backend does NOT need a bundler

```
Node.js CAN DO everything the browser can't:

    1. ✅ IMPORTS WORK NATIVELY
       import express from 'express'
       
       Node.js: "I know where that is.
                 node_modules/express/index.js
                 I'll read it from DISK. Instant."
       
       No HTTP requests. Direct filesystem access.
       500 imports? 500 disk reads. Microseconds each.

    2. ✅ NO JSX (backend doesn't render UI)
       // Backend code is plain JavaScript
       app.get('/api/users', (req, res) => {
         res.json({ name: 'Anna' });
       });
       // No transformation needed.

    3. ✅ NODE.JS RUNS TYPESCRIPT (with loaders)
       node --experimental-strip-types server.ts
       // Node.js 22+ can strip types natively
       // Or use ts-node, tsx: zero bundling needed

    4. ✅ NO CSS (backend doesn't have styles)

    5. ✅ ENVIRONMENT VARIABLES WORK NATIVELY
       process.env.DATABASE_URL
       // OS provides env vars directly to the process

    6. ✅ FILE COUNT DOESN'T MATTER
       500 files on disk? No problem.
       Node.js reads from filesystem, not network.
       No "requests" to load files.


  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │  BROWSER environment:                                       │
  │    - Can only load files via HTTP requests (network)        │
  │    - Only understands plain JS (no JSX, no TS)              │
  │    - No filesystem access                                    │
  │    - No environment variables                                │
  │    - Each file = 1 HTTP request (expensive)                  │
  │    → NEEDS bundler to transform and combine                  │
  │                                                              │
  │  NODE.JS environment:                                       │
  │    - Reads files from disk directly (microseconds)          │
  │    - Has module resolution (knows node_modules)              │
  │    - Full filesystem access                                  │
  │    - Full OS access (env vars, processes, network)           │
  │    - File count is irrelevant (disk, not network)            │
  │    → Does NOT need bundler                                   │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
```

#### How each runs locally
```
FRONTEND (React + Vite):
─────────────────────────

  $ npm run dev
  
  What happens:
    1. Vite starts a DEV SERVER (HTTP server on port 5173)
    2. Browser requests http://localhost:5173
    3. Vite serves index.html
    4. Browser requests JS files
    5. Vite transforms files ON THE FLY:
       - JSX → JS
       - TypeScript → JS  
       - Resolves imports
       - Injects HMR (Hot Module Replacement) client
    6. Browser receives valid JS, renders React app
    
  Hot reload (HMR):
    You edit SearchBar.jsx
    → Vite detects file change (fs.watch)
    → Vite transforms ONLY that file
    → Vite sends update via WebSocket to browser
    → Browser replaces ONLY that component
    → React state preserved. Page doesn't reload.
    → ~50ms from save to update on screen

  Vite dev server IS the app server during development.
  It serves files AND transforms them.


BACKEND (Express + nodemon):
────────────────────────────

  $ npx nodemon server.js
  
  What happens:
    1. nodemon starts node process: node server.js
    2. Node.js V8 parses and executes server.js
    3. Express binds to port 3000
    4. Server is running, handling requests
    
  Hot reload (process restart):
    You edit userRoutes.js
    → nodemon detects file change (fs.watch)
    → nodemon KILLS the entire node process
    → nodemon starts a NEW node process: node server.js
    → Express binds to port 3000 again
    → Server is running with new code
    → ~500ms-2s from save to server restart

  Node.js IS the runtime. No transformation needed.
  nodemon just restarts it when files change.


  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Vite (frontend):                                       │
  │    Transforms code + serves to browser + HMR            │
  │    Component-level replacement (surgical)                │
  │    State preserved. ~50ms.                               │
  │                                                          │
  │  nodemon (backend):                                     │
  │    Watches files + kills process + restarts process      │
  │    Full application restart (nuclear)                    │
  │    All state lost. ~500ms-2s.                            │
  │    In-memory data, WebSocket connections, caches = gone  │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

#### nodemon — what it actually does

```
nodemon is EXTREMELY simple. It does three things:

  1. Watch files for changes (fs.watch)
  2. Kill the current node process (process.kill)
  3. Start a new node process (child_process.spawn)

  That's it. No bundling. No transforming. No compiling.


  $ npx nodemon server.js

  Is equivalent to you manually doing:

  $ node server.js
  # ...edit code...
  # Ctrl+C (kill server)
  $ node server.js
  # ...edit code...
  # Ctrl+C (kill server)
  $ node server.js

  nodemon automates the Ctrl+C → re-run cycle.


  nodemon.json configuration:
  
  {
    "watch": ["src/"],           // which directories to watch
    "ext": "js,json",            // which file extensions
    "ignore": ["tests/"],        // skip test files
    "exec": "node server.js"     // command to run
  }
```

#### Modern alternatives to nodemon

```
Node.js 22 has a BUILT-IN watch mode:

  $ node --watch server.js

  Same as nodemon: watches files, restarts on change.
  No extra package needed.


  $ node --watch-path=./src server.js

  Watch specific directory only.


  For TypeScript:

  # Old way: compile first, then run
  $ tsc && node dist/server.js

  # tsx: runs TypeScript directly (uses esbuild under the hood)
  $ npx tsx watch server.ts
  
  # Node.js 22+: native type stripping
  $ node --experimental-strip-types --watch server.ts


COMPARISON:

  ┌──────────────────────┬───────────┬───────────────────────────────┐
  │ Tool                 │ Install?  │ What it does                  │
  ├──────────────────────┼───────────┼───────────────────────────────┤
  │ node --watch         │ Built-in  │ Restart on file change        │
  │ nodemon              │ npm pkg   │ Restart + more config options │
  │ tsx watch            │ npm pkg   │ Restart + TypeScript support  │
  │ ts-node-dev          │ npm pkg   │ Restart + TS (older approach) │
  └──────────────────────┴───────────┴───────────────────────────────┘
```


#### But wait — some backends DO use bundlers

```
WHEN you might bundle backend code:

  1. TYPESCRIPT PROJECT (common)
  ──────────────────────────────
  
    TypeScript must be compiled to JavaScript.
    
    Option A: tsc (TypeScript compiler)
      $ tsc
      src/server.ts  →  dist/server.js
      src/routes.ts  →  dist/routes.js
      
      Compiles each file separately. Keeps file structure.
      NOT bundling — just transforming TS → JS.
    
    Option B: esbuild / tsup (fast bundler)
      $ tsup src/server.ts
      src/ (50 files) → dist/server.js (1 file)
      
      Bundles everything into one file. MUCH faster build.
      Used for: npm packages, serverless functions (Lambda).


  2. SERVERLESS / LAMBDA (important)
  ──────────────────────────────────
  
    AWS Lambda cold start time depends on package size.
    
    Without bundling:
      Upload: node_modules + src/ = 200MB
      Cold start: 3-5 seconds (loading 2000 files)
    
    With bundling (esbuild):
      Upload: handler.js = 2MB (one file, tree-shaken)
      Cold start: 200ms
    
    Bundling removes unused code ("tree shaking"):
      import { get } from 'lodash'  →  only includes get()
      Not the entire 1MB lodash library.


  3. NPM PACKAGE (you publish a library)
  ───────────────────────────────────────
  
    If you publish a package to npm:
    Users expect: const { search } = require('your-package')
    
    You bundle your src/ into a single dist/index.js
    with type declarations (dist/index.d.ts).
    
    Tools: tsup, rollup, esbuild.


  4. DOCKER IMAGE SIZE OPTIMIZATION
  ─────────────────────────────────
  
    Without bundling:
      COPY package.json .
      RUN npm install              ← downloads ALL of node_modules
      COPY src/ .                  ← copies source
      Image size: 500MB+
    
    With bundling:
      # Build stage
      RUN npm run build            ← produces dist/server.js
      
      # Production stage
      COPY dist/server.js .        ← just one file, no node_modules
      Image size: 50MB
    
    Smaller image = faster ECS deployments.


  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  Regular Express/Fastify server:                          │
  │    Bundling NOT needed. Run source files directly.        │
  │    node server.js works fine.                             │
  │                                                            │
  │  TypeScript server:                                       │
  │    Compilation needed (tsc or esbuild). Not "bundling."   │
  │    Or use tsx/node --strip-types to skip compilation.     │
  │                                                            │
  │  Lambda functions:                                        │
  │    Bundling RECOMMENDED. Reduces cold start dramatically. │
  │                                                            │
  │  npm packages:                                            │
  │    Bundling REQUIRED. Users expect compiled output.       │
  │                                                            │
  └────────────────────────────────────────────────────────────┘
```


#### The full picture — both environments

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  FRONTEND (Browser environment)                                     │
│                                                                      │
│    Source:   JSX, TypeScript, CSS modules, 500+ files               │
│    Problem:  browser can't understand any of this directly          │
│    Solution: Vite transforms + bundles into 3 browser-ready files   │
│    Dev:      Vite dev server (transforms on the fly + HMR)         │
│    Prod:     npm run build → static files → served by server/CDN   │
│                                                                      │
│                                                                      │
│  BACKEND (Node.js environment)                                      │
│                                                                      │
│    Source:   JavaScript (or TypeScript), 50+ files                  │
│    Problem:  none — Node.js runs JS natively, reads from disk      │
│    Solution: no bundler needed                                      │
│    Dev:      nodemon / node --watch (restart on file change)       │
│    Prod:     node server.js (just run it)                           │
│                                                                      │
│              Optional: tsc for TypeScript compilation               │
│              Optional: esbuild for Lambda / npm packages            │
│                                                                      │
│                                                                      │
│  WHY the difference:                                                │
│                                                                      │
│    Browser loads files via NETWORK (HTTP requests)                  │
│      → must minimize file count (bundling)                          │
│      → must transform syntax (JSX → JS)                             │
│      → must resolve bare imports ('react' → actual URL)             │
│                                                                      │
│    Node.js loads files from DISK (filesystem)                       │
│      → file count doesn't matter (disk reads are free)             │
│      → JS runs natively (no transformation needed)                  │
│      → module resolution built in (knows node_modules/)             │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```
